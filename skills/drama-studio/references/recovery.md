# 接续、版本与交付

## 本地与远端

项目目录包含 `research/`、`reference/`、`planning/`、`runs/`、`knowledge/`、`episodes/`、`reviews/`、`deliveries/`（`init-project` 建）。工作中的稿件放 `runs/`，`episodes/` 只放交付副本；C6 的审读记录（`review-record`）放 `.drama/reviews/`，顶层 `reviews/` 只放给人看的阅读记录。`.drama/project.json` 只是绑定与进度提示，`PROJECT.md` 是可读摘要。初始工具不会创建远端项目，也不会证明数据已同步。

正文和记录保存完整文本，注明输入版本／摘要、产物状态和远端回执。项目目录不可放在技能安装目录中。凭据、临时签名 URL 不写入可分享交付包。

自主开发另保留 `planning/development-rNN.md` 及 `planning/experiments/` 中的探索片段；给人看的阅读记录放 `reviews/`。由 AI 按 [创作开发](development-lab.md) 按需建立文件，不修改用户已有记录。`PROJECT.md` 指向当前完整稿、当前探索、输入版本、保护的创作选择、未核实材料与下一动作。安装本身不生成这些创作记录。

## 恢复顺序

1. 先运行 `python3 -B scripts/drama_tools.py status <项目目录>`，按输出第一行处理。第一行的优先顺序：有结果未知的保存回执先对账；其次处理无效或损坏的记录；最近一次运行的快照若引用了旧修订（本地缓存里已有更新的可信修订），第一行是要先运行的 impact 命令，该运行原先的下一步列在第二行，先看 impact 结果再决定，不要直接照做；都没有时才是最近一次运行的 `nextAction` 与未完成项。运行下方写「无法判断是否失效」时，既不能当作未受影响，也不能当作已失效，按原因补齐缓存或扩大阅读；写「本地缓存中没有更新修订」只说本地缓存，不说明远端有没有。它只读 `.drama/` 下的回执、运行与快照，不读聊天记录、不联网，也不证明远端状态、采用或质量；「最近运行」优先按运行记录的 `finishedAt` 判定，没有该字段的按文件修改时间（输出写明 `recencyBasis`），所以写运行记录时要填 `finishedAt`。项目没有 `.drama/` 时退出码 1，此时按下面各步人工恢复。
2. 按 [两次审批](approval-flow.md) 读取选题选择与送审包审批的版本、用户原话和适用范围；缺少记录保持待确认，不能从文件存在、进度或模型推荐推定已批准。再读取本地绑定和上一轮回执；如果远端 projectId 已存在就读取该项目，不重建同名项目。
   [启用了集纲层](outline-layer.md#1-总览c3a--c3b--c3c--c4两处人审不变)的项目接着恢复三样：入口底账修订（`planning/ledger/` 下的 `ledger-ep000.json` 加各集 delta；用 `ledger replay --at <最近一集> --track actual --out planning/ledger/ledger-ep<NNN>.actual.json` 重放出实际轨，没有正文的集用 `--track planned`，`ledger diff` 列出两轨差异）；季编排 `planning/season-plan.json` 的当前修订与各集容量动作；决定队列 `planning/decisions.json`（`decision list --status pending` 列出待决条目，后续工作按各条的默认走，不停下等）。入口状态记录 `runs/state/after-ep-<NNN>.md` 从实际轨重新导出（`ledger replay … --md`），不手写。
3. 发现当前工具，刷新远端任务、页面及其当前修订与标签。远端不可读时只报告缓存状态及其日期。
4. 检查是否有响应未知的提交、尚未同步的本地稿、外部编辑或过期检查。前文有了新修订并缓存后，运行 `python3 -B scripts/drama_tools.py impact <项目目录> --page <pageId> --revision <新修订号>`（历史候选用 `python3 -B scripts/drama_tools.py impact <项目目录> --slot <slot> --revision <n>` 或 `--artifact <artifactId>`）：标为 `stale` 的快照与运行引用了旧修订，是否重新装包、重跑由人决定，工具不自动重跑、不改写正文；运行记录声称产出了这些修订的运行不因此失效，输出里会写明（这是运行记录的说法，工具不核实）；输出带 `warnings` 时先核对页面或 slot 有没有写错；`unknown` 按输出的建议扩大阅读，不当作未受影响；`current` 只说明没有记录在案的执行依赖指向旧修订，内容层面的隐含依赖仍靠阅读判断。
   知识卡更正或退役后（`knowledge/cards/` 里新增了更高修订，或最新修订的 `processing` 改为 `retired`），运行 `python3 -B scripts/drama_tools.py impact <项目目录> --card <cardId>`：只列出装入了这张卡的快照与依赖它们的运行，引用旧修订或该卡已退役的标 `stale`，原因写明“卡 X 已有 rN”或“卡 X 已退役”；只引用最新修订且未退役的标 `current`；本地找不到该卡或记录读不出来的标 `unknown`，按建议扩大阅读。更正后是否改用新修订重新装包、退役后是否去掉这张卡重跑，由人决定，工具不自动处理。按页面或 slot 运行 impact 时，知识卡也照同一规则计入结论。
   同时核对保底稿与探索片段，恢复审读实际看过的内容及阅读测试进行到哪一步。已见结局的上下文不能继续冒充首次预测；需要重测时换未看过的上下文，否则标记事后自评。
5. 指明下一动作和所需输入，继续独立且已获授权的工作。`status` 给出的下一步只来自本地记录，仍要对照审批范围与远端状态；进度依赖聊天记录时先补证据，不能猜造 ID。

反馈修订接续时，同时恢复本轮明确创作目标及未达项；旧稿“可继续编辑”或程序检查通过，不能将人物、对白、情绪的待修问题自动关闭。实际处理按 [人物与情绪改稿](character-emotion.md)，沿用用户约定的样段或全稿范围，不自动扩大。

源码或说明中出现某个工具，不代表当前服务部署了它。页面保存能力缺失时保留本地草稿，不以通用写块接口绕过。正式事实来自当前正文修订（已保存的页面修订）；没保存的本地稿不更新正式连续性。

宿主切换先停止原宿主写入，再移交同一工作目录和项目 ID。本版本没有多宿主写锁或事务性本地版本库，只支持串行接续。不要声称具备并发安全或自动跨设备同步。

并行运行（例如分批并行的多个作者运行）写页面时，各自以读到的修订作为 `expected_revision`。写入返回 409 时分两种：`VERSION_CONFLICT`（别人先写了新修订）与 `IDEMPOTENCY_CONFLICT`（同一 `request_id` 配了不同输入），处理不同，都按 [页面读写](mali-story.md#页面读写版本标签与恢复) 第 3 步做；`create_page` 遇到 `PAGE_ALREADY_EXISTS` 同样先读再定，不直接覆盖。两种都不自动合并，被拒的正文留在本地供比对。分批时约定每个页面只有一个作者运行在写（例如每集一个页面、一批只写本批的集），依赖前一批产出的步骤等前一批保存后再装包。

## 交付

接续前核对正文、集纲、报告中的输入摘要和当前磁盘内容。摘要不同可能是编剧的新修改，不自动恢复旧文件；保留两者，说明冲突，在新版本处理。模拟反馈注明测试来源。删角色／缩场地时，检查其原有信息、行动、交易和情绪功能，不能只删台词或用电话声、旁白偷增演员。明确保留的编剧句子与结局选择单独复核。

跨批次先导出入口状态记录，再写后续：谁已知何事、已完成和未完成的付款／承诺、物件所在、当前故事日；有底账的项目这些就是实际轨，由 `ledger replay --track actual --md` 导出。分集计划是计划，事实来自当前正文修订；不得假定未写出的计划事件已发生。检查批次边界和结尾回收，集纲不能替代完整正文。

按用户选定版本生成：市场与对标依据、参考资料索引、人物设定、蓝图与集纲可读稿、N 集完整正文、检查报告、问题清单、修订对照。核对集数唯一且连续、结局存在、没有占位文本；未完成报告不得写“全部通过”。

提供下限、辨识度、阅读偏好三个独立结论，并标明模型／真人及阅读范围。探索中的故事方案和被放弃方案保留供接续，但与完整正文入口分开；没有真人读者不填留存率、追剧率或采用率。

有具体修改意见时另给本轮目标达成情况、对应新版场面及剩余问题。停止一轮内部修订不等于所有意见已解决；样段获认可也不自动证明未重读的后段成立。

交稿前按 [结果验收](delivery-readiness.md) 核对实际正文，而非只清点文件；提供编剧明确可打开的阅读入口和待反馈问题。制作拆解列出道具不同状态与替身需求，不以单一物件名称低估不可逆操作的成本。

默认可交 Markdown。DOCX、飞书只在当前环境有实际可用导出工具／连接器时使用，不通过改扩展名冒充格式转换。飞书交付读实际导入结果并核对文档；正文修改前先获取当前修订，防止覆盖编剧新稿。没有飞书不会阻塞本地交稿。

用户尚未审阅时标“待确认审读稿”。样稿、完整稿、模型审读通过、用户打标签、制作采用和整剧验收是不同状态。每次交付附实际产物位置、远端 pageId@修订号、待办与下一动作。

发现版本摘要不同时，先盘点目录内的历史副本、外部编辑稿和回执；“未读取旧副本”不能写成“没有旧副本”。交付报告中的缺失声明也要查证。

合并分批正文时，批次封面和状态说明放到交付入口，不插在上一集场景中。保留冻结源文件，单独生成合并稿及映射／差异；补动作标记等机械规范化要列清楚，不能当作剧情提质。约束检查因格式无法核验时，修复新交付副本后重跑，不通过放宽规则消除警告。
