# Validate the handoff manually before building the workflow engine

2026-09-27 · 阶段 0。当前为 `offline_prepared`，不是真人验证通过。

用户明确“目前拿不到反馈”。不将其视为认可、不重复催同一输入、不暂停所有授权内工作；也不绕过真实验证扩大整套工程投入。

## 目标与当前范围

先验证这个最小闭环是否有用：制作人能凭交接包定位具体任务的阻断，编剧能修正该问题，复核人能确认修法没有损失原有功能。先用普通 Markdown 表和原文引用，不先建设六模块引擎。

本次选择三种不同风险的纸面对照：11–13 集能力与伤势规则、43 集解锁救女与视觉任务、60→61 集钩子承接。实际版本、阅读范围、未核点见 [私有离线对照包](../../../../mali-story/_doc/creative/zhenyuan-rescue-2026-09-25/reviews/stage-zero-offline-2026-09-27.md)。这些是主编选出的例子，不冒称导演认定的最难场面。

## 0a：缺反馈时可完成什么

1. 绑定原稿快照与候选 hash，注明粗搭对应版本未知；不覆盖原飞书或正文。
2. 每个案例列原动作、候选动作、修复的因果问题、必须保住的情绪功能，以及修法可能造成的损失。
3. 把画面拆成需要制作人验证的任务，不以场标题数替代镜头数或费用估算。
4. 疑点按类型记录：矛盾查两端及区间，遗漏查义务与覆盖，制作未知列任务和所缺信息，审美保留负责人的取舍。
5. 明确仍可进行的本地工作与暂不可声称的结果；阶段 0 留在 offline_prepared。

已完成的窄解析缺陷可独立修复；测试用原创片段，私稿只作本地只读复测。不得为消除解析警告擅改剧情或设置更宽预算。

## 0b：有实际制作人员时如何验证

参与角色按实际身份登记；同人兼任可以，不伪装多人独立审查。不要求用户现在提供人员或排期。

| 任务 | 执行人实际要做什么 | 留下的证据 |
| --- | --- | --- |
| 接手 | 不依赖聊天记录，找出本次版本、保护范围和未核条件 | 找不到的信息、交接耗时、版本引用 |
| 定位 | 看原文与候选，指出具体哪里不能演/不能做或情绪不成立 | 集场、动作、原因；不只写“整体崩” |
| 试排/拆解 | 核对人物/道具/时空位置，安排动作、声音、停顿和镜头 | 实际覆盖与方法；未演动作不可算进已测片长 |
| 难点验证 | 在另有授权及试前约定的范围内验证高风险任务 | 所有尝试、条件、可用数量、总工时/费用、失败和停止原因 |
| 修复复核 | 编剧改候选，复核正文及实际受影响上下游 | 原问题是否消失、是否新增损失或依赖问题 |
| 判断流程价值 | 比较发现的阻断、漏检、误拦截和维护负担 | 实际记录，不填想象的节省比例 |

试前约定验证问题、预算/工时上限、停止条件与继续/收缩依据；目前均未知。没有付费执行授权，不启动收费试镜。

## 决策出口

- 输入不足：保留 offline_prepared，明确缺口；不认定剧本必然不可用。
- 交接无法让人定位或修复问题：改交接包/结构，减少无效字段，不继续堆系统。
- 闭环真实可用：只把反复出现、成本值得的动作提为自动化候选，不自动推广全项目。
- 制作决定：仍须具体版本、实际资源和有权责任人确认；阶段 0 通过也不是整季制作放行。

不设无反馈超时通过、不预填默认片长、不估虚构复用率。资源须计入同期预约及试制，失效/撤回须重核；旧证据逐项映射，核心 suspected/unresolved 不能偷渡为 eligible。

## 本轮结果边界

已准备对照包、修订方案、手工指南和格式回归；技能的独立模拟检查另见执行回执。未进行真实导演围读、拆镜、试制、经营验证；也未做未提示缺陷位置的长剧跨批依赖盲测。后两类证据缺失时不能声称“精准影响分析”或“流程已证明能避免亏损”。
