## 先说结论

建议保留现有轻量创作工作流，把六项原则变成六个有独立责任、输入、产物和验收依据的模块。不是给写作增加六轮人工审批，而是让“下一步凭什么能做”可查证。

核心变化：先明确制作边界，再建立故事因果与跨季承诺；每批正文留下可追溯状态；独立审查读取正文而非只读作者总结；修改后准确撤销旧证据；真正投入制作前，以小批次实测放行。

## 1. 用户、问题与证据

用户是同时向编剧和短剧视频制作团队交付的创作负责人。当前痛点不是少一个润色提示词，而是导演在做了约 20 集粗搭后才报告后续无法继续；用户将检查范围明确为第 10 集之后。

已核对的本地证据：

| 观察 | 能得出的结论 | 不能据此推定 |
| --- | --- | --- |
| 救援稿已写齐 11–60 集，状态仍是本地候选 | 有可审阅正文，不只是方案 | 已被导演采用或可直接复工 |
| 独立复审、片长、镜头复用、经济结果均未验证 | 交付链缺少这些证据 | 剧本一定不可用，或一定亏损 |
| v1 基线：自定义统计识别 86 个连续场标题，原 episode-check 对 Markdown 场标题识别为 0；本轮源码修复后识别 86 场，仍有格式警告 | 标题格式兼容缺陷已修；未支持内容须继续显示覆盖不足 | 场地为零、成本下降，或工具已经判定质量通过 |
| 现有 skill 已规定连续性、反证、版本失效和两次创作审批 | 不是从零发明原则 | 原则已被可靠执行、已形成统一模块接口 |

来源：当前工作区的 [`PROJECT.md`](../../../../mali-story/_doc/creative/zhenyuan-rescue-2026-09-25/PROJECT.md)、[`delivery-check.json`](../../../../mali-story/_doc/creative/zhenyuan-rescue-2026-09-25/reviews/delivery-check.json)，以及 drama-studio 当前源码。此次设计基线提交为 `0e8b6be8581e88ec4b22a4b134518c137f7dfbd8`。

根因判断分两层：本次已经证实的是证据链和工具格式存在缺口；“这些缺口使叙事问题迟至粗搭阶段才暴露”是合理的流程层推断。具体损失金额、每个剧情问题对停产的贡献，需要导演逐场反馈和真实制作资料，不能由本设计补造。

## 2. 三种互斥的总体方案

以下先谈用户一天怎么工作，再谈系统。数字是设计验收目标或计划假设，不是实测收益。

### A. 编剧自查后整稿交导演

产品：适合独立编剧、暂无制作计划。①收到改稿任务，看旧稿并标问题，得到任务清单；②查看制作条件，补一页清单，得到约束；③逐批写作，自填状态表，得到完整稿；④按检查表自审，得到交稿说明；⑤导演读整稿，决定接不接。价值时刻是把聊天中的要求整理成可复用清单。

相对当前散落记录，目标是每份交付有 1 个版本入口、6 类检查都有记录；但独立读取正文的角色仍为 0，制作风险仍集中在整稿交接。继续使用阈值是记录不比正文难维护；推荐阈值是导演能凭一页摘要接手；垃圾线是填完表便声称可拍。

系统：个人输入为主，提供固定检查模板；项目资料不进入公共资产库。AI 整理与自评、作者决定、导演终审。复用现有 writing/creative-loop；只新增模板。适合低风险探索，不作为此次停产问题的主方案。

验证：验证编剧是否愿意长期维护记录；主要风险是自证循环，其次是表与文不同步，再次是私稿分享。规划成本粗估 1–2 人周，最大成本仍是后期导演返工；无真实工时样本。

### B. 编剧持续创作，证据随稿走，导演分批接手（推荐）

产品：适合已有编剧和制作团队、需要及时止损的短剧项目。①看到原稿及未知条件，确认能确认的项，得到边界；②查看因果与季间承诺，选定保留方向，得到可追踪计划；③按授权写作，看到每批状态变化，得到候选正文；④收到带原文的审查，处理事实问题与审美分歧，得到修订证据；⑤改稿后看到受影响范围，只重查相关部分，得到当前可信版本；⑥导演围读、拆镜与试难镜，得到本批实测；⑦负责人决定本批放行或返修，下一批继续积累证据。

价值时刻：导演不必等整剧粗搭失败，能在首个小批次准确指出“这里状态接不上”或“这类镜头尚未验证”，而编剧能知道修哪一段、保住哪一段。

量化验收目标：所有放行决定必须覆盖本批 100% 集数且有具体版本；所有已确认阻断项必须有该问题类型所需的证据与处理结果（连续性查两端及区间，遗漏查义务和应发生范围）；无有效映射直接沿用旧证据的次数为 0。试点用 3–5 集制作批次，相对用户报告的约 20 集粗搭后发现问题，把首次制作验证点前移；这不等于保证节约某个比例的成本。继续使用阈值是关键缺口可定位；推荐阈值是第二个团队不用解释聊天历史也能接手；垃圾线是自动绿灯掩盖未知。

系统：混合供给。少而稳定的检查模式、反例和匿名测试片段作为可分发资产；私稿、预算、镜头、采用决策为项目输入，绝不自动入库。AI 写作与提取、脚本检查格式和时效、独立评审审正文、导演与制片给实测和放行。复用现有 skill、CLI 与本地项目目录；新增六类产物及交接检查。

验证：先用手工版本包验证“导演能否定位真实制作阻断、编剧能否据此有效修改”，不等待完整工具。阶段 0 同时检查记录负担与误拦截，再决定自动化哪些重复工作。适用于串行本地协作；不承诺跨设备同时编辑。原 4–7 人周仅保留为未校准工程估算，不是获准投入的预算或先于试点执行的计划。

### C. 全团队转入统一在线制作审批系统

产品：适合多人同时改稿、多项目并行的制片公司。①团队迁入项目，看到统一版本；②各岗位提交条件，获得责任分配；③编剧写作，其他人在线评论；④审查与修改在系统内流转；⑤导演上传试镜，制片确认预算；⑥按权限发布制作包。价值时刻是所有人从同一处取得最新可用稿。

目标同样是每个放行范围 100% 可追溯，并新增跨用户同时编辑冲突检测；需要迁移的岗位覆盖编剧、编辑、导演、制片 4 类，而 B 不要求更换他们现有工具。继续使用阈值是日常协作可靠；推荐阈值是多项目管理省事；垃圾线是为了交稿先维护两套系统。

系统：项目输入与集中管理为主，团队资产库沉淀；平台负责权限、持久化、工作队列和审计，AI 提供辅助。现有 drama-studio 不能独自承担；远端正式故事状态仍属于 mali-story，必须另做跨项目产品方案。与 B 在部署边界、数据所有权、协作方式上有实质差异。

验证：验证团队是否愿意整体迁移，而不只是能否建页面。产品迁移成本最高，其次是事务/权限复杂度，最后是数据治理风险。粗估至少 8–12 人周，仅作为比较量级；不纳入此次六模块落地。

工作量比例不凭空填写：三案均按“自动处理项、模型判断项、真人决策项”分责；占比须在试点记录实际工时后给出。选择 B 是本轮设计建议，不授权新增云服务或支出。

## 3. 保留的创作流程

市场与参考研究 → 选题候选 → **用户选题** → 框架、人物小传、完整集纲、前 10 集正文 → **用户批准具体送审包** → 在授权内分批写其余正文。

六模块嵌入其中，不增加六道创作签字：

- M1 在已有题材探索时可先记未知，在正式方案和正文前补足关键条件。
- M2 与送审包一起形成，并在后续候选修改时记录偏离。
- M3、M4、M5 随每批工作；未获得独立评审不能伪称通过，但不当然停止获授权的草稿探索。
- M6 只决定制作移交；写完、编剧采用、导演同意制作、实际经济结果是不同状态。

既有停产剧是修订任务，不重走新选题审批；只保留原授权与冻结边界。写作批次沿用现有配置（通常不超过 10 集），制作试点批次建议 3–5 集，两者不混为同一审批频率。

v1 只交付设计，未改源码或安装目录。v2 获准继续执行；具体已完成的源码、测试和真人验证分别见修订与推进记录，不以设计状态替代执行回执。设计包保留在当前工作区，目标项目仍是 `/Users/jason/dev/drama-studio`。

未来实现继续用 Python 3.10+ 标准库、宿主已有模型能力、本地项目文件；不引入私钥、新模型服务、收费自动任务、新 UI 或数据库。mali-story 保留远端任务、计费和正式采用状态的所有权。

本包的验收是模块设计完整、契约一致、反例可检验。窄工具测试已执行，结果见回执；真实独立审稿、片长试验、导演采用和经营改善仍需各自证据，不因文档或工具完成而自动完成。
