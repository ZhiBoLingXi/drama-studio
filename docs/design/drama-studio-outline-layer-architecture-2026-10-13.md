## 第一页

**现有集纲层的错误假设（一句话）**：一集戏是先定下画面和结果、再往前补理由就能成立的东西，所以集纲可以用「描述一集成片」的六个字段来计划一集没拍的戏，而钱的来路、程序怎么走、三年里各方做了什么、物件在谁手里这类全剧级的事实，可以留给分段作者临场各自决定。

**新架构的核心想法（一句话）**：集纲层拆成四层——全剧功能地图（每条线、每一集要完成的戏剧功能）、底账（前史、钱、物、谁知道什么、程序依据、各方图谋，结构化、逐集有修订号）、季编排（把功能分到集，按媒介物理量算容量，装不下的在这里重排拆删）、分集计划（写正文之前必须定下的东西，剧情自足，声明读写了底账哪些项）；跨线的根缺口先归并成前提问题、定下默认再分线写实现；每个实现在落进底账之前都要过一份不打分的现实追问单，程序与行业做法由检索写成带出处的卡，用户给定的设定同样过；追问出的承重缺口只有三个去处——换实现后经核对确认消失、登记为戏剧假定、进决定队列并带默认；修订只允许回到功能层换实现，换实现的次数有预算，补丁计数到两次就强制回上游；集纲的信息清单、在场与知识状态直接成为台词层对话表的输入，台词层发现装不下或没对象时有通路回到季编排。

## 1. 设计原则

1. **功能先于实现，实现先于画面。** 每条线、每一集先写它要完成什么（观众感受到什么、谁知道了什么、局面怎么变），再找实现；实现被否定时回到功能换实现，不在原实现上补理由。现实审查把这一条写成全剧成因：「先定画面和结果，再倒着补理由」（§五规律一，把握：高）。
2. **全剧级事实只在一处定，而且在分集之前定。** 钱的来路、程序怎么走、空白期各方做了什么、对手每一步图什么、物件在谁手里，都是底账条目，由 C3b 产出并核对；分段作者读它、引用它、提议改它，不写它。结构审查 §7.4 列了七类被留给分段作者的全剧级事（把握：高）。
3. **现实核对是工序，不是审读意见。** 它有固定的问题单、固定的记录格式、固定的「没查到怎么办」；由带检索的代理查出处，由模型答追问单；回答是 `holds / notHolds / not_evaluable` 三态，不是分数（「查过没查到」是底账条目的状态 `unverified`，不是回答的状态）。追问出的承重缺口必须有去处（§6.4）：换实现后经核对确认消失、登记为戏剧假定、或进决定队列并带默认。「一条不成立都没有」不是交接条件——D6-0 的 63 份记录里做到的只有 3 份，而且都是没有改动世界的功能。
4. **用户给定的设定是输入，不是公理。** 标来源，同样过追问单；问题如实列出来，给出通过核对的候选，默认按候选走并标待决，主创随时改。不替主创决定，也不把主创没看过的矛盾当成已定。候选若让某个功能句落空，系统不默认选它：哪个功能可以不要是主创的事，这时默认保留用户给定的实现并登记为待确认的戏剧假定（§9）。
5. **按集变化的状态有逐集的家，而且分计划与实际两轨。** 分集计划声明它读了、改了底账哪些项（计划轨）；正文写出来后由状态变化提案更新实际轨；两轨对不上就报，不覆盖。
6. **容量由媒介物理量推出，在分配时算，在分集之前处理完。** 估时＝信息条数 × 同类处境语料交换中位时长（粗估），与目标时长比；超了的处理动作在季编排层；分集计划只复核；正文层不压台词。数字只触发动作，不判好坏（与台词方案 §3 原则 9 同一条）。
7. **剧情框架自足，其余字段只能派生。** 「本集发生的事」一栏单独可读、含结尾事件、含幕后事件；看点／情绪／爽点若保留，只能从它摘，脚本核它不含新实体。
8. **修订只允许回到功能层，补丁计数到 2 强制回上游。** 审读意见必须引用功能 id 或底账条目；修订单不含替换文字；编排方不得下把修订逼成塞补丁的约束。换实现有预算（C3a 默认 2 次），到顶后承重缺口按 §6.4 登记，流程继续，不再换。
9. **不新增人力；人工反馈来了就吸收。** 主创、编剧、顾问任何时候给的一句话、一份改稿、一条「这个程序不是这样走的」，由脚本回流成底账条目的修订或追问单的新问；流程不等。
10. **每条不变量标 S／R／M，验收只引用 S／R**（系统架构 §4.1）。底账、功能地图、季编排与分集计划首版是本地文件（S 核），页面写入仍走 mali-story（R）。主创 2026-10-14 已定：首版本地；页面化在实施计划 D6-5 再评估。

### 2.3 为什么是四层，不是在 C3 和 C4 之间加一张表

- **功能地图和底账分开**：功能是「要什么」，底账是「世界是什么样」。同一个功能可以换实现而世界不变（礼物线五个功能里四个不依赖「滞留仓库」，现实审查 §2.4），同一条底账被多个功能依赖（「三年里三个叔叔住在临江」同时压着礼物线、三年空白线、监护线）。合在一起，换实现就要改账、改账就要重审功能，修订面积失控。把握：中。
- **季编排和分集计划分开**：容量只能在分配时处理。结构审查 §5.3 的三卷超载来源（框架密、修订塞入）都是在「集数不动」前提下发生的；拆集、挪事件的权限在全剧层，分集作者没有。把握：高。
- **现实核对作为工序而不是审读项**：审读发现问题后修法是打补丁，根源是审读发生在实现已经落进集纲之后（现实审查 §五规律二）。把核对提前到选实现时，被否定的是候选，不是已写的六十集。把握：高。

### 2.4 C3a 与 C3b 之间的顺序，以及前提层

D6-0 按 v1.1 的写法走（先追问、后检索；每条线各写候选），暴露了三件事：检索题目由编排方按线预估，漏了整块程序，追问到后段才发现；101 条查不到出处的规则里有 28 条是追问答完之后才有卡；137 处缺口里 20 处跨线，根是共同的世界前提，分线各写候选会互相顶。顺序据此改成下表。

| 步 | 做什么 | 谁做 | 层级 |
| --- | --- | --- | --- |
| 1 | 功能列表；现行或用户给定的实现登记为候选 A，列 `steps` 与 `ledgerDeps`（一条一个断言） | 写作方 | S：结构；M：把实现整个拿掉，功能句还读得通 |
| 2 | 检索题目由 `ledgerDeps` 里 `kind: procedure` 的断言自动归并（一题可对多条断言），不由人预估；检索代理逐题写 K1 卡 | 脚本归并，检索代理写卡 | S：每题有卡（查不到的是空卡，§6.2）；M：卡的内容 |
| 3 | 候选 A 过追问单；缺口去重，标承重与依据 | 新上下文的核对方 | S：格式、覆盖报告、跨记录一致性（§6.4）；M：答案 |
| 4 | **前提问题**：把跨线的根缺口归并成若干前提问题，每题 2–3 个真不同的候选、一个默认、一条决定 | 写作方 | S：每题有默认与决定队列条目，候选不少于两个；M：候选是否真不同 |
| 5 | 前提带出的新检索题目（未核假设里标了 `collapseIfFalse` 的优先）→ 再检索 | 同第 2 步 | 同第 2 步 |
| 6 | 默认前提的组合过追问单（对象类型 `premise`），由新上下文作答；填跨前提一致性表 | 核对方 | S：表无空格；M：答案与表的内容 |
| 7 | 分线写候选实现，用 `requiresPremise[]` 引用前提；过追问单；选定 | 写作方 → 核对方 | §2.2 的交接条件 |

```text
function-map.premises[]
  premiseId, question                       # 一个跨线的世界前提问题
  candidates[]: {candidateId, description, origin,
                 unverifiedAssumptions[]: {claim, collapseIfFalse: bool},
                 weakensFunctions[], losesFunctions[]}
  default: candidateId, defaultReason
  decision: decision-queue id               # kind: premise
  inquiryRef                                # 默认候选的追问记录
```

- **检索是迭代的。** 前提写出来以后才知道它靠哪些未核的假设站着；这些假设是新的检索题目。D6-0 做了四批检索、50 张卡，后两批都是追问与前提带出来的。流程是「功能地图 → 检索 → 追问 → 前提 → 再检索 → 再追问」，不是一趟。
- **卡到得比追问晚怎么办。** 回答记录记下作答时读到的卡修订（`cardRevisions`）；卡新增或修订后，`impact --card` 标出按旧卡答的、需要重答的回答（§6.5）。
- **跨前提一致性表**有三张：逐方的总时间线（每一方在每个时段做了什么、没做什么、为什么）、钱的总表（每笔的来路、去向、谁能动、留痕）、谁知道什么。脚本只核格数（每格有内容，或有 `unstated`、`whyMissing` 这类登记），内容由模型填。项目特有的表（例如某部剧需要一张「谁在哪一集已经认识某人」）是项目的数据，由功能地图的断言决定要不要，不进技能规则。逐方总时间线就是 §3.2 的总账视图，这一步要求它在底账写出之前就能从 `ledgerDeps` 生成。
- **它为什么不是新增的人审点。** 前提的决定走决定队列，带默认，流程按默认继续；用户给定的前提默认保留并标 `license_pending`（§9.1）。主创什么时候看、看不看，都不挡后面的步骤。
- **把握。** 「不归并前提，分线各写会互顶」把握高（D6-0 第一轮：七个前提逐题求解后拼起来，互相顶的有 13 处）。「归并之后能收敛」把握低：D6-0 两轮前提都没有通过追问单，而且那两轮没有本稿 §6.4 的分判与 §9.1 的默认，所以它们不能证明这个结构在新规则下走得通，只能证明旧规则下走不通。这要等 D6-0 续（实施计划 §4.1）。

## 3. 底账的对象与字段

### 3.1 通用结构与两条轨

```text
ledger-entry
  id                      # 稳定 id，如 L-money-003
  kind                    # timeline | money | object | knowledge | procedure | agenda
  title                   # 一句话
  origin                  # user_given | designed | derived_from_text（正文写出来后登记的）
  status                  # asserted | verified | unverified | contested | license_pending | accepted_license | retired（各自的意思见 §3.8）
  conflictsWith[], conflictKind   # status: contested 时必填；分类见 §3.8
  humanWords              # status: accepted_license 时必填：主创的原话
  introducedAt            # pre（前史）| ep<N>
  realityRef[]            # K1 知识卡 id（有出处时；引到卡里的条）
  inquiryRef[]            # reality-check 记录 id
  notAsked                # 没有被任何追问落到；为 true 的条目不得标 verified
  tension                 # 可选：与别的条目不互斥、但放在一起别扭，只登记
  dependents[]            # functionId、episode
  patchCount              # 被修补过几次（§8.2）；迁移旧项目时查不到的填 null
  history[]               # {rev, change, by: C3b|C4|C5-actual|feedback, when}
  <kind 专有字段，见 3.2–3.7>
```

```text
ledger-delta（分集计划与正文都产出）
  episode, track: planned | actual
  reads[]: entryId
  writes[]: {entryId | new, change: {...}, reason}
```

- `ledger@ep000` 是前史账，C3b 产出；`ledger@ep<N>.planned` 由脚本把第 1..N 集分集计划的 `writes` 依次应用得到；`ledger@ep<N>.actual` 由正文的 `stateChangeProposals` 应用得到。两轨差异脚本报，交下一集 C4 作为输入（它接的是实际轨）。这是系统架构 §6.4「集纲说明准备发生什么、正文说明实际写了什么、状态索引不覆盖正文」在集纲层的落法。
- 一条底账条目被改，脚本列出 `dependents` 里的功能与集，这是修订面积的依据（§8）。
- 3.2–3.7 的字段表按 D6-0 的第一份真实底账（400 条）改过；改的原因与各状态、矛盾分类的定义集中写在 §3.8。

### 3.2 时间线账（timeline，含谁在哪）

| 字段 | 装什么 |
| --- | --- |
| `when` | 故事日／时段，或前史的相对时间（「事故后第 7 天」） |
| `who`、`where` | 谁、在哪（在场核对读这个） |
| `did` / `didNot` | 做了什么 / 没做什么（至少填一个，不要求两个都有） |
| `why` | 为什么（没做的也要有为什么）。材料没给时不编：留空并标 `whyMissing`（缺，脚本报）、`whyNotApplicable`（这条不需要理由）或 `whyPartial`（只给了一半）之一 |
| `unstated` | 材料对这一方在这段时间什么都没写。登记为一行空白，不是省略 |
| `knownTo[]` | 当时谁知道这件事发生了 |

为说明而编的例子（§5 的那条线）：

```text
L-tl-012  kind: timeline  origin: designed  status: verified  introducedAt: pre
  when: 三年前十二月、两年前十二月、去年十二月
  who: 姑姑阿芬  where: 海外渔船（合同期三年，每年只靠岸一次）
  did: 每年从靠岸港寄一件生日礼物到舅舅家地址；寄后在手机上看到「已签收」
  didNot: 没有打过视频（船上没有信号；靠岸时打到舅妈手机，三次都被告知孩子睡了）
  why: 她以为孩子收到了（签收记录），没有理由起疑
  knownTo: 舅妈桂姐（签收人）
  realityRef: [K1-远洋渔工合同期与通讯条件]   # 由检索代理查，若没查到标 unverified
```

**空白期总账**是时间线账的一个视图：脚本按 `when` 把某一段（如「事故后三年」）里所有各方的 `did`/`didNot` 列成一张表，追问单第 13 问对着这张表答。现实审查 §五规律三说「三年空白被当成设定，没人回头算总账」，这张表就是总账。这张视图在 C3a 阶段、底账写出之前就要能从功能地图的 `ledgerDeps` 生成（§2.4）：D6-0 里它是追问时另写的，89 行里 52 格的理由材料没有给，有三方整行为空。这是脚本可以核的「缺」（`why-missing`、`unstated`），不必等追问单去问出来。

### 3.3 钱的账（money）

| 字段 | 装什么 |
| --- | --- |
| `amount` | 数额量级（不是精确数；精确数在正文层按出处定） |
| `from`、`to`、`account` | 来路、去向、进了谁名下的什么账户 |
| `whoCanMove` | 谁有权动（这决定了「侵吞」在现实里要走什么手续） |
| `trace` | 留痕：转账记录、回单、签字、票据 |
| `procedureRef` | 这笔钱的发放／领取依据（程序账条目） |

```text
L-money-002  kind: money  origin: user_given  status: unverified  introducedAt: pre
  amount: 一次性抚恤金，量级「几十万」（出处待查）
  from: 用人单位经工伤保险基金  to: 近亲属  account: 舅舅名下存折
  whoCanMove: 领取人须证明近亲属身份与代未成年人领取的资格 → 这一点决定舅舅能不能一个人领走
  trace: 银行流水、领取申请上的签字
  procedureRef: L-proc-004（工亡抚恤金领取）
  inquiryRef: [RC-0007]   # 第 8 问「这笔钱怎么到他账上的」答 unverified：领取资格没查到
```

现实审查 P03、P60 的问题（补助金领取人要有监护身份、按月抚恤金三年没人提、退赔无来源、七叔被骗的钱无人追）都是这张账里 `whoCanMove`、`from`、`trace` 三个字段空着造成的（把握：高）。

材料没给的字段登记在 `emptyFields[]` 里。它是登记，不是豁免：`money-closed` 照样报，一直报到有人补上（`pre-select` 阶段记为报告，不拦，§3.8）。D6-0 的底账里 20 条钱的条目共有 43 格空字段。

### 3.4 物件账（object）

| 字段 | 装什么 |
| --- | --- |
| `object` | 什么东西 |
| `holder`、`location` | 在谁手里、在哪 |
| `howItGotThere` | 怎么到那儿的（引用时间线条目） |
| `state` | 状态（未拆、烧毁、在证物袋） |
| `visibleTo[]` | 谁知道它在那 |

```text
L-obj-005  kind: object  origin: designed  status: verified  introducedAt: pre
  object: 三件刻着「阿禾」名字的生日礼物（三年各一件），原包装未拆
  holder: 舅妈桂姐  location: 舅舅家阁楼杂物箱（阁楼上锁，孩子不许上）
  howItGotThere: L-tl-013（桂姐三次签收后搬上阁楼）
  state: 未拆
  visibleTo: [桂姐]
  dependents: [F-gift-2 三年礼物同一刻出现, ep07, ep08]
```

每集分集计划 `writes` 改 `holder`/`location` 时，脚本核「单链」：一件东西在同一修订里只能在一处；从 A 到 B 必须有本集的事件支撑（`howItGotThere` 指向本集某场）。结构审查 §6.3 列的哨子五段各说各的、手环第 57 集说不松第 59 集就解、账本三层——都是这条核对要抓的（把握：高）。

### 3.5 知识账（knowledge）

| 字段 | 装什么 |
| --- | --- |
| `who` | 谁 |
| `knows` | 知道什么（一条一个事实） |
| `since` | 从哪一集哪件事起知道；允许细到拍（`beatId`），否则分集计划核不了「说这句话之前他知不知道」 |
| `how` | 怎么知道的（在场／被告知／推断；引用时间线或场） |
| `notKnows[]` | 明确不知道什么（这是对话表 `listenerKnows` 的来源）。一条知识条目可以只记 `notKnows` 而没有 `knows` |

```text
L-kn-021  kind: knowledge  origin: designed  status: asserted  introducedAt: ep07
  who: 阿禾
  knows: 姑姑每年都寄过礼物
  since: ep07 场 7-3（桂姐当着姑姑把三件礼物搬下来）
  how: 在场
  notKnows: [礼物里有没有别的东西, 姑姑为什么三年没回来]
```

脚本核**单调性**：知道了不能变成不知道，除非本集登记「被骗」「忘了」类事件；一个人在某集「说出」一件事，知识账里他必须在此之前「知道」它（`stage-d` §六第 4 条：家宝说出他不该知道的「抽屉的钥匙」，就是这一条没核）。观众的知识单独记（`who: 观众`），信息清单每条对应一条观众知识的 `since`。

### 3.6 程序与机构账（procedure）

| 字段 | 装什么 |
| --- | --- |
| `name` | 程序或行业做法的名字（快递拒收退回、人身安全保护令、事故调查报告期限…） |
| `realWorldRule` | 现实里怎么走：步骤、谁经手、几天、要什么条件、留什么记录 |
| `currentClaim`、`claimVsRule` | 材料现在是怎么写的；它与 `realWorldRule` 的出入（一致／相反／材料没写） |
| `nextNecessaryMove` | `{mandated, customary}`：条文规定这个机构接下来必须做的事（`mandated`，须引卡）与办案常规上通常会做的事（`customary`，没有出处，一律按未核对待）。追问单第 4 问对着它答 |
| `state` | 程序走到哪一步；到季末仍是启动了没有出口的，脚本报出 |
| `realityRef[]` | K1 知识卡（出处）；没有就 `status: unverified` |
| `usedIn[]` | 哪些功能、哪些集依赖它 |

```text
L-proc-002  kind: procedure  origin: designed  status: verified  introducedAt: pre
  name: 快递被收件人拒收后怎么走
  realWorldRule: 快递员录「拒收」，寄件人端当天可见；联系寄件人确认退回；退回件送到寄件人处签收；
                 只有寄件人联系不上才成无着件，保管期自登记起不少于一年；按件处理，不按寄件人合箱
  nextNecessaryMove: {mandated: 联系寄件人确认退回, customary: 无}
  realityRef: [K1-无着快件规定]
  usedIn: [F-gift-1（被否定的候选 A）]
```

程序账是**项目的数据**，不是技能的规则：每部剧涉及哪些程序由功能地图的 `ledgerDeps` 决定，技能只规定「有依赖就要有条目、条目要有状态」。这就是「架构通用、项目差异进数据」在这一层的形态。

`nextNecessaryMove` 分两级是 D6-0 逼出来的：条文通常只给期限与职责，「机构必然会逐个问证人、必然会调某类档案」这类判断没有出处；不分级时第 4 问要么一律答不了，要么把常识当成规则。

### 3.7 各方图谋账（agenda）

| 字段 | 装什么 |
| --- | --- |
| `party` | 哪一方（人或组织） |
| `goal` | 此刻要什么 |
| `means` | 可用的手段与边界（「只用律师函、举报，不设黑社会背景」这类口径放这里） |
| `constraints` | 做不了什么、为什么 |
| `nextMove` | 按他的利益，下一步最省事的做法是什么（追问单第 1、2 问对着它答） |
| `validFrom`/`validTo` | 这条图谋在哪段有效（对手的目标会变） |

```text
L-ag-003  kind: agenda  origin: designed  status: asserted  validFrom: pre  validTo: ep08
  party: 舅妈桂姐
  goal: 让姑姑相信孩子过得好、不来接
  means: 签收并藏起礼物；接电话时替孩子回话；不扔礼物（刻了名，扔了怕被捡到问）
  constraints: 姑姑一旦当面见到孩子，说法就守不住 → 所以她要阻止见面而不是编更多话
  nextMove: 姑姑回国那天带孩子出门「补课」
```

对手每一步图什么，现行是五段 notes 各写一份、集纲看点逐集再写一遍（结构审查 §7.4）；放进这张账后，分集计划只引用。登记范围：被程序条目或时间线条目引用的图谋必须登记，只在单场之内起作用的不登。同一方在重叠时段的两条图谋，手段互斥的由脚本报（`agenda-exclusive`，§10.2）。

### 3.8 条目状态、矛盾分类与分段写账

**状态怎么区分。**

| 状态 | 意思 | 追问时 | 进哪份清单 |
| --- | --- | --- | --- |
| `asserted` | 设计中，还没核 | 照常问 | — |
| `verified` | 有出处，或落到它的各问都成立；`notAsked` 的条目不得标 | — | — |
| `unverified` | 查过，没查到出处 | 引用它的回答记 `not_evaluable` | 未核清单 |
| `contested` | 与另一条互斥 | 照常问 | 交接前清零（见下） |
| `license_pending` | 追问出它不合常规或没有出处，系统按 §9.1 的默认先保留，等人确认 | 已登记，不再作为未处理的 `notHolds` 拦交接 | 戏剧假定清单（标「待确认」）＋决定队列 |
| `accepted_license` | 主创明知不合常规仍要保留；须有 `humanWords` | 同上 | 戏剧假定清单 |
| `retired` | 换实现后退役 | — | — |

`asserted` 是还没查；`unverified` 是查了、不知道对不对；两种戏剧假定是查了、知道它与常规不合或没有出处、仍然留着。三者在送审包里的去处不同，不能互相代替。D6-0 之前系统只有前两种，用户给定的若干场面恰好在现实里没有出处或方向相反，结果只能被判不成立或被拿掉（中期报告第四节第 3 条）。

**矛盾分类。** `contested` 的一对条目带 `conflictKind`：

| `conflictKind` | 是什么 | 怎么处理 |
| --- | --- | --- |
| `world` | 两条断言在同一个世界里只能成立一头 | 回 C3a 换实现，或登记决定 |
| `source_variant` | 用户给定的写法与现行材料的写法不同 | 进决定队列，默认按 §9.1 |
| `layer_variant` | 两层现行材料（如框架与集纲）对同一件事写法并存 | 系统内定以哪层为准，不进决定队列 |
| `rule_implied` | 两句字面不相顶，互斥来自 K1 卡上的规则 | 记所依据的卡；卡被修订时这类矛盾重判 |

另有一类不是两条条目之间的：同一方的两条图谋互斥（§3.7），由 `agenda-exclusive` 报。D6-0 的底账里矛盾 23 对：`world` 13、`source_variant` 3、`layer_variant` 3、`rule_implied` 1、图谋互斥 3。

**「`contested` 为零」什么时候核。** 选定候选、旧实现的条目标 `retired` 之后才核。在此之前底账登记的是候选 A 的世界，矛盾本来就该在；这一段叫 `pre-select` 阶段，`ledger check --stage pre-select` 对矛盾、`why` 缺失、钱的空字段只报不拦。D6-0 只跑到这个阶段，选定之后的规则没有在真实数据上通过过。

**状态性断言没有合适的位置。** 「谁是某人的监护人」「某人此刻的人身状态」这类带起止时间的法律、人身、关系状态，六类账里放不好。是加第七类 `status`，还是在时间线账下加一个子型，列为 D6-1 的设计决定（实施计划 §2.8）。D6-0 的临时做法是放进时间线账并标 `whyNotApplicable`。

**分段并行写账要先有 schema。** D6-0 把底账分三段并行写，同名字段的记法在三段之间漂移（单数与复数、字符串与对象），跨段的补充只能靠 `amendments[]`。设计上：分段写之前 schema 已定；`ledger merge` 支持跨段 `amendments`，并校验同名字段类型一致。

**规则从真实数据反推。** 按 v1.1 字段表直接写出的格式规则，对第一份真实底账报了 108 条假阳性（例如要求每条时间线同时有 `did` 与 `didNot`），放宽七处后才可用。D6-1 的 schema 以 D6-0 的三段真实底账作夹具反推必填项，不从本稿的字段表照抄。

## 4. 分集计划的字段表

字段 14 个，必填 9 个（标 ●）。「谁核」里 S 是脚本、M 是模型。每个字段都写明不装什么，因为结构审查 §三证明现行字段的病不在缺字段，在字段装了不该装的东西。

| # | 字段 | 装什么 | 不装什么 | 必填 | 谁核 | 怎么核 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `episode`、`title` | 集号；标题（派生，可改，不是约束） | — | ● | S | 集号与季编排一致 |
| 2 | `entry` 入口状态 | 引用的底账修订号（有正文时是上一集**实际轨**）；一两句：故事日与时段、主要人物在哪、手里有什么、此刻知道什么 | 上一集钩子画面的复述（「接……」）；作者解释 | ● | S＋M | S：修订号存在且等于上一集出口修订；M：一两句与账一致 |
| 3 | `functions[]` 本集功能 | 引用功能地图里的 functionId，写本集把它推进到哪一步（「观众第一次看见礼物；阿禾知道姑姑寄过」） | 新功能、新线（要新的回 C3a） | ● | S | id 存在；季编排把它分到了本集 |
| 4 | `events` 本集发生的事 | **自足**：结构化为 `scenes[].beats[]`——按场写（每场：`sceneId`、时间、地点、在场），场内按拍写（每拍有 `beatId`）谁做了什么、因为什么、结果如何；含幕后／对手的事（标 `offscreen`）；含**集末最后发生的事**；需要的台词写引号里的原话 | 镜头指示、尺度指示、留给正文的话（「数额留正文」）、跨集呼应说明、人物辩护（「他没有变蠢」）、作者对心理的解释 | ● | S＋M | S：每场有时间地点在场；`exit.closingEvent.beatRef` 指向最后一场的最后一拍；派生摘要的实体集合 ⊆ 本栏实体集合；M：冷读者只读本栏能复述谁在场、发生了什么、停在哪（§10.3） |

| 6 | `moves[]` 关键动作 | 每个改变局面的动作：`who`、`did`、`wants`（此刻要什么）、`easierOption`（更省事的做法是什么）、`whyNot`（为什么没做）、`cost`（代价）；**对手的动作必有**；主角的「选择」也写在这里 | 复述事件；别人的解释；「在她的算法里」类心理旁白 | ● | M | 追问单第 1、2、3 问逐条答（§6.3）；答「不成立」的回 C3a |
| 7 | `infoLedger[]` 信息清单 | 观众在本集必须拿到的事实，每条带 `facts[]`（一个 fact 一个事实，有 `factId`、承载它的拍 `carrierBeat`、供复述对照的 `keywords[]`）；每条：`whyAudienceNeeds`、`laterDependents[]`（后面哪集靠它）、`knownByInStory[]`（戏内谁知道，引用知识账） | 情绪、氛围 | ● | S＋M | S：每条有对应的观众知识条目 `since: 本集`；`facts` 非空；M：是否真是必须 |
| 8 | `ledgerDelta` 状态变化 | `reads[]`、`writes[]`：知道了什么、东西到了谁手里、钱怎么动、关系怎么变、程序走到哪一步 | 不引用底账的自由文本 | ● | S | id 存在；应用后物件单链、知识单调、钱的 from/to 闭合；`writes[].supportedBy` 是本集存在的 `sceneId` 或 `beatId`（引用，不是自由文本） |
| 9 | `realityRefs[]` 现实依据 | 本集用到的程序账条目 id ＋ 当前状态（verified/unverified） | 新的查证（查证归 C3b）；「凭常识写」类备注 | 涉机构／程序／技术时 ● | S | 每个引用存在；`unverified` 的条数进本集报告与送审包清单；`contested` 为零 |
| 10 | `threads` 承接与埋设 | `pays[]`：兑现了哪条（引用 plantId）；`plants[]`：埋了哪条、季编排里预定在哪集回收 | 「第 N 集要用」类散句 | 有埋设或兑现时 ● | S | pay 的 plant 存在且在前；plant 在季编排有回收位 |

| 12 | `capacity` 容量 | `infoCount`、`sceneCount`、`estimateSec`（§7 公式）、`targetSec`、`basis`（语料快照）、`status: fits | proposal:<id>` | 任何「字数上限」 | ● | S | 脚本算；超出时提案 id 存在；**不是通过条件** |
| 13 | `pending[]` 待定项 | 引用决定队列条目 id ＋ 本集采用的默认走法 | 「待主创定」而没有默认走法的句子 | 有待定时 ● | S | 队列条目存在；默认走法非空 |
| 14 | `summary` 派生摘要 | 可选：看点、情绪、爽点各一两句；给 mali-story 页面和与拉片对照用 | 任何 `events` 里没有的事件、人物、物件、台词 | 可选 | S＋M | S：人名／物件／动词集合 ⊆ `events`（粗核，报不拦）；M：是否只是摘要 |

**现行六字段去哪了**：剧情框架 → 第 4 栏（必须自足，不封顶）；关键选择 → 第 6 栏（动作带动机与放弃项，不单设）；情绪铺垫、核心爽点、核心看点 → 第 14 栏派生（可选，不许含新事件；主创 2026-10-14 已定保留为可选）；结尾钩子 → 第 11 栏 `closingEvent`（是事件）。260 字上限废除（出处不明，结构审查 §十）。

**最小够用**：第 1–4、6–8、11、12 九个字段。少了 2 就没有入口、少了 3 就不知道这集为什么存在、少了 4 就不自足、少了 6 就没有动机可核、少了 7 台词层没有输入、少了 8 底账断链、少了 11 下一集接不上、少了 12 容量回到正文层。5、9、10、13 按条件必填，14 可选。

**为什么结构化到拍，以及这部分的把握。** v1.1 里 `supportedBy`、`closingEvent` 是「场 6-2」这样的自由文本，脚本核不了它在不在；「说话人此前知道」的「此前」只到集或场，核不到「本集哪一拍之前」。D6-0 写临时脚本时把它们改成了对 `sceneId`／`beatId` 的引用，给 `facts[]` 加了 `keywords[]`，容量字段加了画面拍数。**这些改动只经过合成夹具的自测，没有在真实的分集计划上跑过**——D6-0 没有走到分集计划这一步。把握：中（结构上必要），字段是否够用：低。

## 6. 现实核对的方法

### 6.1 核什么

五类前提，每类都可能是地基：

| 类 | 例（来自现实审查的类型统计） | 谁查 |
| --- | --- | --- |
| 程序与机构（31 条，最多） | 监护顺位、保护令时限、事故调查期限、无着快件、刑事程序期限 | 检索代理 |
| 行业做法 | 快递拒收怎么录、园区消防队员遗物由谁清理、报警主机屏蔽后手动按钮是否触发 | 检索代理 |
| 物理与技术 | 过火闪存三年后能否读、哨声在暴雨里传多远 | 检索代理 |
| 心理前提 | 六岁孩子三年不拧开每天戴着的夹层 | 模型答追问单第 3 问；查不到出处 |
| 动机与利益 | 拒收还是签收对他更有利、冷静商人会不会亲自见证人 | 模型答追问单第 1、2 问 |

**各类实际占多少（D6-0，四条线的候选 A）。** 137 处缺口按类型数（一处可以属于多类）：材料缺写 50、动机 40、内部矛盾 39、知情 26、后果或机构动作没写 21、与现实规则相反 15。检索能直接判定的只有最后一类，是少数；多数是没写、互相顶、谁知道什么对不上、逐个动作问不出动机。两轮前提追问是同一个形态：第 9、10 问（程序规则、技术前提）没有一处不成立，只有查不到出处；第 1 问（更省事的做法）与第 13 问（总账）每个前提都不成立。所以这道工序里，检索的作用是把程序名目对上并留出处；现行集纲的病主要靠另外两样东西抓——底账的脚本规则（缺写、互斥、知情，§10.2）和追问单的 A、B、E 三组（动机、他人与机构、总账）。把握：中（一个项目；缺口的判断全部由模型作出，没有人看过）。

### 6.2 检索代理做什么、不做什么

- **输入**：检索题目，由功能地图 `ledgerDeps` 里 `kind: procedure` 的断言自动归并而成（脚本归并，一题可对多条断言）；底账写出后再加上程序账里 `status: asserted` 且 `realityRef` 为空的条目。每题带材料的当前写法。题目不由编排方按线预估：D6-0 预估时漏了整块程序，追问到后段才发现。
- **迭代**：检索不是一趟。前提写出来以后，它靠着的未核假设是新的题目（§2.4）；标了 `collapseIfFalse` 的先查。
- **做**：按条目检索公开资料（法规、部门规定、行业报道、技术文献），写一张 **K1 知识卡**（现有 `knowledge-card` schema：`evidence.sources[].location` 为外部 URL 时标 `external_not_checked`，原文片段存进 `knowledge/sources/<sourceId>/`，`usage: comparison_only` 或 `creative_reference`），卡上写：查到的规则、与条目当前写法的出入、适用条件、来源日期。
- **不做**：不改剧情、不给改法、不判「这段戏成不成立」；它只把「现实里怎么走」摆出来。成不成立由追问单答。
- **没查到**：条目 `status: unverified`，卡上写查了什么、没查到什么；不编造。
- **K1 卡的写法约定**（不改 `knowledge-card` schema，D6-0 暴露）：
  - 内容按条写，每条标 `sourced`（有出处）、`inferred`（推断，无出处）或 `not_found`（查了没查到）；`realityRef` 引到条。一张卡里常常是几条有出处、几条是推断，整卡一个状态分不清引的是哪一级。
  - 整张卡没有一条有出处的，标为「空卡」。引用空卡的回答只能是 `not_evaluable`，空卡不能支持任何「通常怎样」的说法。D6-0 的 50 张卡里空卡 5 张。
  - 来源分三级：官方原页、转录本或转载、已失效的旧版。写进 `versionOrDate` 与 `limits`。D6-0 的多数条文取自转录本。
  - 引公开个案时写清个案的情形，以及它与本剧情形不同构的地方；追问单引个案时须带上这些差异。
  - 这些约定是否升为 schema 字段（条目级 `support`、卡级 `coverage`、`sourceTier`、个案的 `caseFacts` 与 `distanceFromOurs`），列为 D6-1 的设计决定（实施计划 §2.8）。
- **标准是卡，不是审查。** 两份审查是模型写的，自身有无出处或与条文不符的说法；D6-0 里卡与审查有出入的至少 5 处。追问单只认卡；与审查的对照只作旁证。
- **检索代理可以联网检索，这是技能的正式做法**（主创 2026-10-14 已定，写进 `references/outline-layer.md`）：有检索能力的宿主查公开资料并留出处；边界是随包脚本永不联网（CLAUDE.md 的规矩不动），检索是宿主模型的能力，不是本地工具的功能。
- **宿主没有检索能力时**：同样标 `unverified`，并在 `run-handoff.unknowns` 写明「本次无检索」。

### 6.3 追问单（全部问题）

对象是一个**候选实现**（C3a 选实现时）、一个**前提**（C3a 前提问题的候选，§2.4）或一个**关键动作**（C4、修订时）。每一问的答案落到具体的步（`stepId`）、断言（`depId`）、集／场／动作或底账条目，写 `holds / notHolds / not_evaluable` 加原因；涉及出处的引用 K1 卡并引到条；不打分、不合成。

**A. 动作与动机**

1. **更省事的做法**：这个人要达到他的目的，现实里最省事的做法是什么？他为什么没做？（答案必须是一个具体障碍，「他没想到」不算）
2. **图什么**：这一步做成了他得到什么？做不成失去什么？（对手每一步必问；答不出就是没目的）
3. **心理前提**：这个年龄、这种处境的人会这样想、这样做吗？（孩子的三年、母亲的五年、商人的亲自下场）

**B. 机构与他人**

4. **机构的必然动作**：这个机构按常规接下来必然会做什么？写了没有？没写的话它为什么没做？（民警看到挂锁和旧伤、调查组看到维保作业单）
5. **其他知情人**：这段时间里其他知道这件事的人会做什么？逐个列。
6. **多久被发现**：这件事按现实多久会被发现？谁最先发现？为什么到现在没被发现？

**C. 信息与物**

7. **怎么知道的**：这个人是怎么知道这件事的？信息链上每一环（谁告诉的、什么时候、在不在场）都有吗？
8. **怎么到这儿的**：这件东西／这笔钱是怎么到这里的？经过谁的手？留了什么痕迹？谁有权动？
9. **名目后面的实体规则**：这个程序的名字后面，谁有资格、几天、什么条件、谁经手、留什么记录？出处是什么？
10. **物理与技术前提**：这个前提成立吗？出处？

**D. 巧合与后果**

11. **巧合**：这是不是用来解难题的巧合？（开场的巧合可以有一个；解难题的巧合不行）
12. **后果**：按现实这件事的后果写了没有？（谎报警情、违反保护令、公开他人流水、孩子的脸被拍）

**E. 总账与前提**

13. **空白期总账**：这段时间里每一方做了什么、没做什么、为什么？后来加在这段时间上的每一样东西（本地的亲戚、按月的钱、签了协议的证人、出租的房子）一起算过吗？对着时间线账的总账视图答。
14. **去掉实现，功能还成不成**：不用这个实现，功能能不能用别的方式完成？（能的话，这个实现是被画面绑架的，候选里要有另一个）——信息题，不判成立与否，不参与 `outcome`。
15. **是不是用户给定**：这个前提是用户给的吗？如果是，上面每一问同样问过了吗？——信息题，不参与 `outcome`。

**F. 知情**

16. **凭什么知道他据以行动的事实**：这一步里行动的人，此刻凭什么知道他据以行动的那件事？信息来源是哪一环？

问题单是数据（`reality-check-questions.json`，版本化）；项目可以增问（带来源：人工反馈或 `feedback-ingest` 派生），不能删问。每问带 `answerKind ∈ tristate / informational`；第 14、15 问是 `informational`。脚本只核格式（每答有落点、有三态、有原因），不核答案对不对。

- **第 16 问的来源与写法。** 它来自第 6 集台词验证（说话人说出了他不该知道的事）。那里的原话落点是句子；追问单的对象是候选实现与关键动作，没有句子可引，所以题干按上面这样写。对话问题单的第 16 问另写题干（说话人凭什么知道，并入「为问而问」，见台词方案 §8.3）。两份问题单各写各的，不共用一句。
- **第 14、15 问为什么是信息题。** 第 14 问答「能换」不等于这个实现不成立；按三态记会让所有可替换的实现都判不成立。D6-0 里这两问的答案写在原因里，不计入成立与否。
- **主力是 A、B、E 三组。** 见 §6.1 的统计：缺口里与现实规则相反的是少数，两轮前提追问里 C 组的第 9、10 问没有问出一处不成立。追问单真正问得出东西的是动机（A）、他人与机构（B）、总账（E）。
- **追问单不管的。** 追问单的落点天然是动作，知识、图谋、时间线三类断言没有一问会逐条去落；这三类由底账脚本管（知识单调、说话人知情、`why` 缺失、图谋互斥，§10.2）。同理，文内数目自相矛盾、两条断言只能成立一头、启动了的程序没有出口，也归底账脚本，不加问。靠「某事没发生」才成立的断言（`assertion: absence`）不过三态，由总账视图与 `why-missing` 核。
- **v1 → v2 的合并候选**（D6-1 的设计决定，本次不改题干，见实施计划 §2.8）：在候选实现这一层，第 1 与 2 问、第 4 与 9 问、第 5 与 6 问、第 7 与 16 问常常答成同一件事；第 10 问题干太空；第 5 问缺「知情人为什么没说」；第 13 问宜拆成两问。「可增不可删」是对项目而言的规则，问题单从试点版到正式版的合并不受它限制。

### 6.4 结果怎么记录

```text
reality-check
  checkId, target: {kind: candidate | premise | move | ledgerEntry, id}, questionsVersion
  cardRevisions: {K1 id: rev}                # 作答时读到的卡修订
  answers[]:
    q: 1..16
    landsOn: stepId | depId | "ep07 场 7-2" | ledgerId
    holds: holds | notHolds | not_evaluable | n/a
    reason
    realityRef?: K1 id（引到条）, ledgerRef?
    # holds == notHolds 时：
    defectKey                                # 同一处缺口用同一个键，去重用
    defectKind                               # contradicts_reality | missing | internal_conflict | motive | knowledge_gap | consequence_unwritten
    loadBearing: bool, loadBearingBasis      # 作答的核对方填：去掉这一步，哪个功能句落空
    inheritedFrom?: checkId, inheritedAt?: {q, landsOn}    # 缺口在上游实现，不在本对象
    patch?                                   # 对象是换过的实现时：四种不允许的修法之一（§8.1）
    disposition?                             # 承重时必填：三个去处之一及其引用（见下）
    # holds == not_evaluable 时：
    because: no_card | card_says_not_found | cannot_answer
    leaning?: against | for | none           # 没有正面依据，但查到的规则都指向一边
  closes[], retiresWith[], leavesOpen[]      # 上一个实现的缺口在本实现下的结局（见下）
  mapErrata[]                                # 作答时发现的功能地图转述错误
  outcome: pass | fail | fail_inherited | pass_with_unverified
  unverifiedList[]: ledgerId
```

**`outcome` 只是摘要，不作排序或通过的依据。** 任一 `notHolds` 即 `fail` 的记法，在 D6-0 里 49 个候选判了 46 个 `fail`，分不出「调度上的一处」与「地基上的三处」，没有区分力。保留它是为了一眼看出记录里有没有不成立项；`fail_inherited` 表示不成立项全部转引自上游实现。

**交接条件是「没有承重且未登记的 `notHolds`」。** 一条承重的 `notHolds` 只有三个合法去处，记在 `disposition`：

| 去处 | 条件 | 引用什么 |
| --- | --- | --- |
| (a) 换实现后不再出现 | 须有**新上下文的核对记录**确认；写作方自报不算 | 确认它的核对记录 id |
| (b) 登记为戏剧假定 | 底账条目 `status` 为 `accepted_license`（有主创原话）或 `license_pending`（系统按 §9.1 的默认先保留） | 底账条目 id |
| (c) 进决定队列并带默认 | 队列条目存在且 `default` 非空 | 决定队列条目 id |

不承重的 `notHolds` 留在 `leavesOpen`，进送审包附录，不拦。层级：脚本核的是「每条 `loadBearing: true` 的 `notHolds` 有 `disposition`，且它引用的对象存在、状态相符」（S）；这条缺口承不承重、是不是真的不成立，是模型的判断（M），不进验收。

**承重由谁标。** 由核对方在作答时填，并写依据：去掉这一步，哪个功能句落空。不事后推——D6-0 事后推出来的 89 处承重里，55 处只因为落在可以换的实现上才被算作承重，有记录原话或下游转引支撑的是 34 处。

**缺口对新实现的三种结局。** `closes[]`（这处缺口在新实现下不再出现）、`retiresWith[]`（它所在的实现整段退役了——不算修好）、`leavesOpen[]`（仍开着）。`closes[]` 只在核对记录确认之后才计入。D6-0 第二轮：写作方自称上一轮 45 处承重缺口里 36 处不再出现，新上下文核对只确认 18 处，另有 9 处换了地方、8 处是靠把实现拿掉、10 处仍在。

**覆盖与一致性（`check-answers`，只报不拦）。** 覆盖由答题人自己挑时会漏：D6-0 一条线上有 8 条断言、3 个步骤没有被任何回答落到。`check-answers` 加覆盖报告，只算步骤与 `procedure`／`object`／`money` 三类断言（另三类归底账脚本，§6.3）；加跨记录一致性，列出同一个步骤或断言在不同记录里三态不一致的（D6-0 的 49 份记录里有 5 处以上）。一个候选的共用步骤只由一份记录作答，别的记录转引。

**「没写」类结论要写查的范围。** 「材料全程没有写到某事」这类回答，须写明查了哪些集、用的什么办法（通读、关键词、功能地图登记）。D6-0 的核对方对后 50 集的这类结论靠的是功能地图登记与关键词检索，没有通读。

**功能地图勘误。** 追问时对着原文才会发现功能地图转述有误（D6-0 有 3 处）。记进 `mapErrata[]`，C3a 交接前清零。

`pass_with_unverified` 的 `unverified` 列表一路带到分集计划的 `realityRefs` 和送审包的「未核清单」。现行四份 notes 的「凭常识写、未查法条」清单（约 60 项）就是这份清单该有的形态，只是现在它没有去处。

### 6.5 没查到怎么办

- 条目标 `unverified`，不拦截；分集计划可以写，正文可以写，但每一处都带着这个标记走到送审包。
- 送审包附「未核清单」：每条写依赖它的功能与集。主创看一眼就知道哪些地基是常识、哪些有出处。这不是向主创提项目级问题，是如实报告状态。
- 主创或任何人哪天给了出处或说「不是这样」，`feedback-ingest` 把它回流成 K1 卡或条目修订；`dependents` 列出受影响的集，走 §8 的修订。
- 「未核实」不等于「没问题」：追问单其余各问照答；一个 `unverified` 的程序名目下面，「谁有资格、几天」这些字段仍要有写法，只是标为假设。
- 「未核实」也不等于「戏剧假定」：前者是查了、不知道对不对；后者是查到了相反的规则或确认没有出处、明知如此仍然保留（§3.8、§9.2）。两份清单在送审包里并列，不合并。
- 卡到得比追问晚：回答的 `cardRevisions` 记着它是按哪一版卡答的；卡新增或修订后，`impact --card` 列出要重答的回答。D6-0 有 28 条未核规则是追问之后才有卡的，其中至少一处后到的卡指向与原回答相反的方向（两头并列，等重答）。

## 7. 容量与季编排

### 7.1 容量怎么算

与台词方案 §3.2–§3.5 共用一套物理量和口径，本稿不另造：

- 媒介档案：`format`、`targetSeconds`、`speechRate`、`pauseShare`，来源 `corpus_default / project_measured / assumed`。
- **季编排层粗估**（本稿新增的位置）：每集 `Σ(信息条数 × 同类处境语料交换中位时长)` ＋ 登记的画面拍（每拍按语料无台词段中位时长），与 `targetSeconds` 比。画面拍的时长现在量不出来：语料只有对话交换，没有整集时间轴上的纯画面段。所以 `media-profile` 标 `pictureBeatSec: assumed`，D6-4 从原始转写的时间码量；在那之前，粗估里画面拍这一项的把握低。
- **分集计划复核**：同一公式，用分集计划的 `infoLedger` 重算。
- **正文精估**：台词方案 §3.3（口播量 ÷ 语速 ÷ (1 − 停顿比)）。

数字的用途只有两种：算术（估时对目标）和描述（对标单集 1–4 件事、1 个场景，结构审查 §5.4；这是让人知道成片长什么样，不是配额）。它不进任何通过条件。

### 7.2 装不下在季编排层怎么处理

估时超过目标时，季编排的动作三选一，并且**必须选一个**（不是登记待定）：

| 动作 | 做什么 | 代价登记 |
| --- | --- | --- |
| 重排 | 把功能挪到相邻集；或把一集的两个功能分给两集 | 受影响的 plant／pay 位置重登 |
| 拆集 | 一集变两集，总集数变 | 送审前自由；送审包批准后是方向变更，走 `approval-flow.md` §4 |
| 删线 | 某条线的某个功能不实现 | 功能地图标 `dropped` 并写 `droppedCost`（非空：哪条功能落空、后面哪集受影响） |

主创已定「数字不当裁判」：这里的数字触发的是「季编排必须选一个动作」，不是「这集不合格」。选哪个由功能与人物决定（哪个功能在这一集非完成不可、哪个可以等），数字只告诉你装不下。系统自己选的默认只在重排与拆集之间：删线等于让一个功能落空，按 §9.1 的同一条理由，它只能作为决定队列里的选项，不能由系统默认走。

### 7.3 与送审、与台词方案的时序

- 送审包之前：季编排把全部 60 集（或约定集数）的容量算完、处理完，送审包里的分集计划每集 `capacity.status: fits`（或带已批准的 `proposal`）。这样第 6 集那种「写完才发现是 3.5–4 集的量」不会再在正文层发生。
- 送审包之后：任何一层再超（分集计划复核、正文精估），走台词方案 §3.5 的提案队列，流程不停，稿子标 `proposal_pending`。`stage-d` §十第 7 条的意见（粗估超目标两倍先选拆法再写对话表）在新架构里自然成立，因为粗估发生在季编排层，早于对话表。

### 7.4 季编排对象

```text
season-plan
  revision, basedOn: {functionMap, ledgerRev, mediaProfile}
  episodes[]: {episode, functions[], eventsRough[], star: bool, capacity: {estimateSec, targetSec, status, action?}}
  threads[]: {plantId, plantedAt, payAt}
  decisions[]: decision-queue id
```

框架 v3 的「分卷蓝图」（每卷戏核、压力源、代价、兑现、进出状态）保留为季编排的卷级视图；第九节「分集节拍表」废除（它已被各集集纲取代，而且是「先画面后理由」的产地）。

## 8. 修订规则

### 8.1 修订动作只有一种

审读指出承重问题 → 定位到功能 id 与底账条目 → 在 C3a 为该功能换实现（或标 `dropped`）→ 新实现过追问单 → 更新底账（`dependents` 列出受影响的集）→ 重写受影响的分集计划 → 重核受影响的线。

不允许的修法有四种。前三种来自现实审查 §五规律二，第四种是 D6-0 第二轮暴露的。核对方对换过的实现作答时，把认出的修法记在回答的 `patch` 字段：

| `patch` 值 | 是什么 |
| --- | --- |
| `added_explanation` | 在原实现上加一拍解释 |
| `layered_on_same_spot` | 在原处再叠一层（换了程序名目而实体规则不查，也属这一种） |
| `moved_elsewhere_or_coincidence` | 把不可信挪到别处，或挪到巧合上 |
| `removed_instead_of_solved` | 把实现拿掉，功能句落空 |

为什么要第四种：「不许加解释」与「现实只认卡」同时成立时，写作方最省事的出路是把站不住的实现整个拿掉。D6-0 第一轮被判为补丁的 22 处是前三种（加一拍解释 8、原处加一层 5、挪到别处或巧合 9）；第二轮换候选之后缺口少了，但 8 处是靠拿掉，功能句落空 14 条。而哪个功能可以不要，不是系统能默认决定的（§9.1）。

这四种修法连同下面三条，是 C3a 写作任务书的随包条款（M：写作方照做；S：核对记录里 `patch` 字段在，带 `patch` 的缺口不计入 `closes[]`）：

1. 多个前提、多个相互依赖的功能一起选，不逐个求解之后再拼。
2. 每引入一个知情人、一份文书、一个账户，先写出它按常规接下来会做什么。
3. 每个默认候选里，标了 `collapseIfFalse` 的未核假设至多一条。

**修订范围按功能的四种情形定**（D6-0 对账时的分法）：自身没有缺口、只被上游实现拖累的，保留实现、换上游；自身有缺口但都不承重的，原地补并计 `patchCount`；自身有承重缺口的，回 C3a 换实现；没有缺口的不动。

### 8.2 补丁计数

- 每个 `selected` 实现和每条底账条目带 `patchCount`；修订时如果实现 id 不变、只改描述或只加条目，计数 +1；换实现（新 id）计数归零。
- `patchCount ≥ 2` 的实现：S 拒绝再次以「不换 id」的方式修订，必须回 C3a 换实现。
- 迁移旧项目时历史修补次数常常查不到，也量不到「往别处加东西」这种非原地的修补：`patchCount` 允许为 `null`（未知），`patch-cap` 对 `null` 不触发。
- 这是流程触发条件，不是质量判定；它的依据是现实审查对礼物线的追溯（三轮审读都在「签收/拒收」「七张/二十一张」「钩子被放掉」上修，没碰流程本身，§2.3）和补充 4 的「补丁叠补丁」（P76）。把握：高。主创 2026-10-14 已定：接受为流程触发条件，不只作提示。

### 8.3 编排方约束

- 不得下「不动集数」「不动标题」「不动★位置」「只改一次且不拆集」类约束（S：`task.constraints[]` 扫词表，命中即拒，与台词方案 §11「数值型台词约束一律不许下」同一机制）。
- 修订预算（`task.revisionBudget`）算的是**换实现的次数**，不是「只许改一次描述」。在 C3a 默认 2。到顶后的动作是写死的：仍在的承重缺口按 §6.4 的 (b)、(c) 登记（戏剧假定，或进决定队列并带默认），流程继续，不再换。D6-0 没有这条：「写 → 追问 → 换 → 再追问」的回路没有预算，也没有到顶之后的动作，两轮不收敛后只能停。
- 审读 finding 必须带 `functionId` 或 `ledgerId`（S）；两者都没有的归「偏好」，不进修订单（与台词方案 §10.3 同）。

### 8.4 决定队列

「待主创定」现在滞留三轮（现实审查 §五规律五）。新对象：

```text
decision-queue entry
  id, kind, raisedAt: {layer, runId}, question, options[], default: optionId, defaultReason, affects[]: {functionId|ledgerId|episode}
  # kind 见实施计划 §2.1 #7；D6-0 后加 premise（前提一级的取舍）与 license（按现实改掉 vs 作为戏剧假定保留）
  # options[] 每项可带 losesFunctions[]：选它会让哪些功能句落空
  status: pending | decided, decidedBy?, decidedAt?, humanWords?
```

规则：提出决定的人必须给默认走法；流程按默认继续，受影响的分集计划在 `pending[]` 引用它；主创任何时候决定，`feedback-ingest` 回流，`affects` 列出要重写的集。没有「等主创」这个状态。前提一级的决定与「保留还是改掉」的决定同样带默认（§9.1）；默认是「保留用户给定的」，所以流程按默认走不会替主创删掉任何功能。

## 9. 对用户给定设定的处理

- 用户给的设定圣经、梗概、前文，进系统时拆成功能（「这条设定要完成什么」）与底账条目（「它断言世界是什么样」），条目标 `origin: user_given`。
- 追问单对 `user_given` 一字不少地问（第 15 问就是为此设的）。答「不成立」的，不改用户的条目；怎么走见 §9.1。
- 现行做法是「把用户给定当成不可质疑的前提，只在其上修补」（礼物箱、监护资格、三年空白都源自圣经，现实审查 §二、P37、§五规律三）。新做法不比现行多问主创任何事，只是把矛盾摆出来而不是埋进补丁。

### 9.1 默认走法

主创 2026-10-14 已定：按通过核对的候选先走并标 `pending`，不停在该线等主创。这条不变。D6-0 之后给它补了前提与另一半默认（**这是对主创第 3 条决定的细化，待主创确认，见实施计划 §8；确认前按下面的默认做，可逆**）：

| 情形 | 系统默认 | 登记什么 |
| --- | --- | --- |
| 存在通过核对、且不让任何功能句落空的候选 | 按该候选继续，标 `decision: pending` | 决定队列：「用户给定实现 vs 候选实现」，默认为候选；分集计划 `pending[]` 引用 |
| 在修订预算内，每个通过核对的候选都让某个功能句落空（`losesFunctions[]` 非空），或没有候选通过 | **保留用户给定的实现**，底账条目标 `license_pending`；流程按「保留」继续 | 决定队列（`kind: license`）：「按现实改掉」（逐项列代价：哪些功能句落空）对「作为戏剧假定保留」，默认为保留 |
| 前提一级的取舍（§2.4） | 同上一行：默认保留用户给定的前提并标 `license_pending` | 决定队列（`kind: premise`） |

- 候选对象在 `weakensFunctions[]` 之外加 `losesFunctions[]`，每项是 `functionId` 加落空的那半句（感受／谁知道／局面变化里的哪一半）。`losesFunctions[]` 非空的候选不得被系统标 `selected`，只能作为决定队列的选项（S）。
- 为什么这样定：它同时守住两条规矩。一条是「流程不等、不新增人审点」——有默认，按默认走；另一条是「哪个功能可以不要是主创的事」——默认是保留，系统不替主创删功能。D6-0 第二轮正是因为没有这一条，写作被推向把实现拿掉（8 处靠拿掉，功能句落空 14 条，用户给定的锁定被换掉或只保一半的有 8 组）。
- 代价如实记：按「保留」走下去的集建在一条已知不合常规的设定上；主创事后若选「按现实改掉」，`affects[]` 列出的集要重写。所以这类条目在送审包里不藏在附录深处（§9.3）。

### 9.2 戏剧假定

有些场面是类型承诺要的，在现实里却走不通或没有出处。v1.1 的系统只有成立、不成立、未核三态，这类场面只能被判不成立或被拿掉。新增两个底账条目状态（定义与对照见 §3.8）：

- `accepted_license`：主创接受，明知不合常规仍然保留。须有 `humanWords`（主创原话）；没有原话的不得标（S）。
- `license_pending`：系统按 §9.1 的默认先保留，等人确认。

两者都算「已登记」：依赖它的回答不再作为未处理的 `notHolds` 拦交接（§6.4 的去处 (b)）。但登记不是抹掉——条目、依赖它的功能、依赖它的集，全部进送审包的「戏剧假定清单」。追问单其余各问照常对它问：一条戏剧假定只豁免它自己那一处不合常规，不豁免由它带出的别的缺口（知情、动机、后果）。

### 9.3 送审包里的四份附录

| 附录 | 装什么 | 位置 |
| --- | --- | --- |
| 设定核对报告 | 每条 `user_given` 条目的追问结果、候选实现、默认走法 | 首页（§16 第 3 条） |
| 戏剧假定清单 | `accepted_license` 与 `license_pending` 的条目（后者标「待确认」），各自依赖的功能与集 | 紧接设定核对报告 |
| 未核清单 | `unverified` 的条目，各自依赖的功能与集 | 与戏剧假定清单并列 |
| 决定队列 | 全部待决与已决条目，带默认 | 其后 |

主创看到的是「你给的这条在现实里走不通的地方、我们打算怎么保住它的功能、哪些是照你给的留着的」，不是一个项目级问题；决定权在主创，流程不等。

### 10.3 冷读复述怎么做（对计划）

新上下文，只装某一集的 `events` 字段（去掉其他字段），任务：复述谁在场、按顺序发生了什么、因为什么、停在哪；列「我不知道为什么会这样」。脚本对照 `infoLedger`（每条 retold/partial/missing）与 `exit.closingEvent`（有没有复述到）。`missing` 回 C4。它检验的是「写正文的人只看这一栏会不会丢承重点」，正是结构审查 §一担心的那件事。

### 10.4 局限（老实写）

1. **追问单的答案是模型给的**，第 1、3、11 问尤其要对人有感觉；会把不成立判成成立。对策是每答必落到动作、必给原因、涉出处必引卡，让错判事后可见；没人看就留着。
2. **检索代理查到的也可能错或过时**，K1 卡只标 `external_not_checked`，不声称已核验；法规类出处标日期，项目可以要求「某日期之后的来源」。
3. **底账一致性只核结构**，核不出「这条账写错了但自洽」。一条 `verified` 的程序条目写错了实体规则，脚本看不出，只有下一次检索或人工反馈能纠。
4. **冷读者是模型**，和台词方案 §8.6 一样，它读文字比观众拿到的多；对计划层这个偏差小一些（计划本来就是给人读的文字）。
5. **补丁计数能被绕过**：换一个 id 但内容只改一句。对策是 S 核新旧实现描述的字面重合（8 字档，沿用 `dup-check`），重合高的报 `renamed_patch` 提示；仍是提示不是拦截。
6. **没有人工裁判就不能宣称「成立」**，只能宣称「追问单每问成立或标未核、底账自洽、计划自足、台词层没有退回」。四者都成立的集仍可能无聊。首读判效果，但首读也是模型。有意接受。
7. **「承重」是模型的判断。** 交接条件靠它分流，而它没有人看过；D6-0 的 137 处缺口、89 处承重全部由模型判定。对策只有一条：作答时就写依据（去掉这一步哪个功能句落空），让错判事后可见。
8. **同一件事不同的核对方会判得不一样**（D6-0 的 49 份记录里 5 处以上，含结论相反的）。跨记录一致性报告只能把它们列出来，不能判谁对。
9. **前提一级的取舍系统解不了。** D6-0 的根缺口在故事前提上：它每个成立的版本都要换掉一样用户给定或已改定的东西，写作方两轮各选了一样去换，换完都在别处重开同型的缺口。新规则给的是一个不替人做主的默认（保留并登记），不是解法。
10. **读没读全，编排方核不了。** D6-0 的写作方与核对方多次自报没有读全任务书要求的材料。设计上让运行在交接里留下「读到了什么」（`run-handoff.readScope`），核对方据此知道哪里要补核；它仍然是自报。

## 14. 被否决的替代方案

| 方案 | 为什么不够 | 把握 |
| --- | --- | --- |
| **给现有六字段加几个字段**（入口、出口、在场、信息清单…） | 加字段不改「框架封顶、其余不封顶」的流向；结构审查 §九 2 证明剧情会流向不封顶处。而且六字段的分工本身没有规定（§8.2(一)），加到十字段只是多四处可以藏剧情的地方。最要紧的是它不解决上游：钱、程序、三年总账仍留给分段作者 | 高 |
| **加一轮更严的集纲审读**（比如专门审现实合理性） | 已经有五段共 104 条集纲审读加一份 76 条现实审查；审读发生在实现落进集纲之后，修法只能是补丁（§五规律二）。审读越严、补丁越多（第 33 集为答一条意见加六件事）。核对必须前移到选实现时 | 高 |
| **让主创先把设定想清楚** | 违反「不向主创提项目级问题」；而且主创给的设定圣经已经是「想清楚」的产物，问题在系统把它当公理（§九）。正确的做法是系统追问、给候选、主创拍板 | 高 |
| **把底账塞回设定圣经**（扩写圣经的时间线、道具、信息阀门表） | 圣经是全剧级一次性文件，按集变化的状态没有逐集修订号，脚本核不了单链与单调；五段作者正是因为这个才各自在 notes 段末建一套 | 高 |
| **让检索代理直接改剧情** | 它查的是现实，不是戏；改剧情要回功能层选实现。混在一起就成了「查到什么写什么」，功能丢了 | 中 |
| **给每集一个「现实合理性分」** | 数字当裁判；一个分数把 15 个可核的具体问题压成一个没人能核的数；与台词方案否决「对话打分」是同一个错 | 高 |
| **让分段作者自带现实核对** | 五段作者各写一份「凭常识写、未查」，各写一份对手理由，没有一份回到框架（§7.4）；核对要在一处做、一处存 | 高 |
| **不建功能地图，直接按底账重写集纲** | 底账只回答「世界是什么样」，不回答「这集为什么存在」；没有功能层，换实现时不知道要保住什么（礼物线五个功能四个不依赖仓库，这个判断只有功能层能做） | 中 |
| **只核对手和机构，不核主角** | 现实审查的承重问题里有一条是主角的心理前提（六岁孩子三年不拧夹层，P47） | 高 |
