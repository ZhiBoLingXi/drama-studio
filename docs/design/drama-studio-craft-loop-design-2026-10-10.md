# 工艺闭环设计：从“台词 AI 味”出发

日期：2026-10-10 · 状态：设计提案，未实施 · 依据：[系统架构 v1.2](drama-studio-system-architecture-2026-09-29.md)、[知识设计](drama-studio-knowledge-harness-design-2026-09-29.md)、[实施路线图](drama-studio-implementation-roadmap-2026-09-29.md)

## 1. 问题与结论

编剧反馈：AI 写的台词“AI 味重，不像人说的话”，并手写了正例。对照后差别集中在五处：没有称呼对象、省主语和对仗的格言句、只陈述不带态度、书面用词、一句话用来塞信息而不是表态。

结论：这不是台词单独的问题，是一类问题的第一个实例。**凡是脚本量不出来、标准在编剧脑子里的工艺质量**（台词口语、人物声音区分、情绪节奏、钩子力度、爽点兑现），现有流程都缺同一样东西：把编剧的判断变成材料、送进上下文、单独过一遍、再量出来有没有变好的闭环。所以设计成通用的“工艺闭环”，台词是第一个维度。

## 2. 成因

| 层 | 成因 | 证据 |
| --- | --- | --- |
| 模型 | 中文剧本的默认语域偏书面；同一模型自审时带着同样的盲区 | 两读都没指出台词不自然 |
| 规格 | 一集的事件数对字数预算过满，台词被压缩 | 每集 1000–1200 字，集纲单集常有三四个事件 |
| 方法 | 技能里关于台词的规则全是“少说”：能用动作不用台词、不解释、不总结；没有一条说怎么像口语 | `writing.md`、`season-run.md`、`character-emotion.md` |
| 上下文 | 人物小传写性格和经历，不写这个人怎么说话；没有方言口径；没有例句 | 作者包只有圣经、集纲、状态 |
| 审读 | 首读看效果，次读对事实和目标，没有一道只听台词 | `c6-review.md` |
| 反馈 | 编剧改过的句子只留在聊天或页面修订里，下一集的包里没有 | 没有采集通道 |

只加禁令（“不要格言句”）治不了：模型会换一种书面腔。能把输出拉向口语的只有正例，并且是这个人物、这种方言、对这个对象说话的正例。

## 3. 通用性：四个方向

**跨工艺维度。** 一个维度由五样东西定义：编剧的正例从哪来、存成什么卡、装进哪个包、哪一遍专门处理、用什么量。台词、情绪节奏、钩子都按这五项填表，流程和工具共用。

**跨项目。** 声音分层，越上层越通用：

| 层 | 内容 | 存在哪 | 谁写 |
| --- | --- | --- | --- |
| L0 通用口语 | 口语与书面的差别、常见 AI 腔的对照（合成例子） | 技能包 `references/` | 维护者 |
| L1 类型与平台 | 短剧台词直给、带态度、一句一个意图 | 技能包；工作室可覆盖 | 维护者／工作室 |
| L2 地域与年代 | 东北话、粤语区、80 年代用语的词表和例句 | 工作室级知识库（`scope.level: studio`） | 编剧，跨项目复用 |
| L3 人物 | 称呼习惯、口头禅、句长、嘴硬还是爱吹、对不同人的说法，加 5–10 句认可的例句 | 项目知识卡，同时是 C2 产出 | C2 起草，编剧确认 |
| L4 场面 | 此刻对谁说、想要什么、情绪 | 集纲与状态记录 | C4／C5 |

私有剧本的句子只进项目或工作室知识库，不进分发的技能包（沿用现有规则）。L0／L1 只用合成或有授权的例子。

**跨宿主与模型。** 所有规则落在材料和记录上，不依赖某个宿主的能力；只有“另起上下文审读”需要宿主支持，做不到时如实记为自审，关口判不通过。宿主支持时，台词审读优先用另一个模型家族，因为同家族有同样的盲区；记录里写明是哪一种。

**跨语言变体。** 脚本不内置任何方言或口语词表作为标准。统计只和本项目里编剧认可的例句比，标准由例句给出，换方言、换题材不用改工具。

## 4. 系统架构

### 4.1 数据：不新增对象类型

沿用 `knowledge-card`（已有 `scope.level: project|studio|public`、`processing: pending→curated`、`usage`）：

- **声音卡**：`knowledgeType: K5`。每个主要人物一张，`content` 写称呼、口头禅、句长、方言词、态度倾向和例句；`limits` 写不适用的场合（如正式场合会收着说）。
- **对照卡**：`knowledgeType: K9`。一张一组：AI 原句、编剧改句、差在哪、适用的人物／方言／意图。`evidence` 指向出处（页面的两个修订，或编剧的原话）。
- 卡的 `content` 用约定的小标题，便于检索和统计；是否需要给这两种卡加结构校验，试点后再定。

人物声音表同时存成一个 `characters` 语义的页面修订，供主创在网页上看和改；知识卡是它进入上下文的形态。

### 4.2 采集：三个通道，都进 `pending`，编剧确认后 `curated`

1. **直接给**：编剧贴“原句→改句”，宿主整理成对照卡。
2. **页面修订差异**：编剧在网页上改了 AI 写的页面，就有了一个 producer 不是 AI 的新修订。新增离线工具 `harvest`，读同一页面两个已缓存的修订，逐场对齐，抽出被改动的台词行，生成候选对照卡。它只做文本比对，不判断好坏，“差在哪”由宿主起草、编剧确认。
3. **审读记录**：台词审读里被采纳的改法，定稿后转成候选卡。

通道 2 最重要：它不要求编剧额外做事，改稿本身就是标注。

### 4.3 检索与装包

- 作者包和台词包按本集出场人物取声音卡，按人物、方言、意图取对照卡，用现有的 `knowledge search`。
- 知识分区设上限（建议不超过包的四分之一），每个出场人物至少一张声音卡，对照卡优先取同一人物、最近确认的。超了就少装对照卡，不截断正文。
- 例句放在包里靠后、靠近写作指令的位置；写明“学说法，不照抄句子”。

### 4.4 流程：C5 拆两遍，C6 加一读

1. **C4 预算**：集纲阶段核对单集事件数与字数规格。装不下时提 C4 变更（拆集或减事件），不让正文靠压台词解决。
2. **C5 第一遍，场面**：照现在的方法写场面、动作和台词初稿。
3. **C5 第二遍，台词**：单独一个运行，包里只有本集稿、出场人物的声音卡、对照卡和状态记录。只许改台词行。脚本可查：两稿之间非台词行逐字相同，场头集合不变。
4. **C6 台词读**：新上下文，只给台词、说话人和对象，不给集纲。逐句标“不像这个人会说的”并给改法；另做一次“盖住名字猜是谁说的”，猜不出说明人物声音没分开。
5. 台词读的问题并入那一次定向修订，不增加修订轮数。

第 3 步独立成一遍的理由：和场面一起写时，模型的注意力在因果和信息上，台词会退回默认语域；单独一遍时目标只有一个，且可以换模型。

### 4.5 关口与度量：分清脚本能查的和只能人判的

| 类别 | 内容 | 标记 |
| --- | --- | --- |
| 脚本查 | 每个有台词的出场人物都有 `curated` 声音卡，并装进了作者包 | S |
| 脚本查 | 有台词运行，且它只改了台词行 | S |
| 脚本查 | 有新上下文的台词读记录 | S |
| 脚本算，只作提示 | 台词行平均长度、带称呼或语气词的比例、无主语短句比例、人物之间的用词重合度、口头禅出现次数，均与本项目认可例句的同一统计比较 | 统计，不判通过 |
| 脚本算，作指标 | **台词人工改动率**：编剧下一个修订里改掉了多少条 AI 台词（由页面修订差异得出） | 统计 |
| 人判 | 盲选：同一场的两版台词不标来源，编剧选更像人话的一版 | 人审 |

台词好不好，脚本不下结论。真正的指标是人工改动率：它来自编剧的实际行为，不用额外打分，能逐批、逐项目比较，也能用来比较模型和提示方案。

### 4.6 评测

`evals/` 加一组对照评测：留出一批对照卡不给作者看，让各方案盲改同一批 AI 原句，由编剧盲选。用来回答三个问题：声音卡加对照卡有没有用、台词单独一遍有没有用、换模型有没有用。

## 5. 风险

| 风险 | 对策 |
| --- | --- |
| 口头禅泛滥（已出现过一句口头禅全季上百次） | 口头禅次数进统计；声音卡写明频率；并入重复追踪（D4 遗留项） |
| 方言写成漫画腔 | L2 卡由编剧确认；`limits` 写什么场合不用 |
| 例句被照抄 | 包内写明只学说法；`dup-check` 对台词与例句做重合统计 |
| 人物之间串味 | 对照卡按人物标注，默认只取本人物的 |
| 包变大、成本上升 | 知识分区上限；台词遍只装本集稿，不装全量设定 |
| 候选卡质量差 | 一律 `pending`，编剧确认才进包 |
| 把“口语”当成新模板 | 声音卡保留“这个人不这么说话”的反例；直说、少话的人物照样成立 |

## 6. 分期

| 阶段 | 做什么 | 验收 |
| --- | --- | --- |
| P0 试点（不写代码） | 编剧给一部剧的声音例句和 20–30 组对照；手工建卡；3 集按“两遍加台词读”重写 | 编剧盲选，新版被选中的比例 |
| P1 方法与契约 | `c2`、`c5`、`c6` 文档加声音卡、台词遍、台词读；L0／L1 参考文档（合成例子） | 新会话按文档能走通 |
| P2 采集与指标 | `harvest`（修订差异→候选对照卡）、台词统计、人工改动率 | 夹具上结果可复算 |
| P3 关口 | `season-check` 加三条 S 检查 | 合规通过，逐条破坏只报对应规则 |
| P4 工作室知识库 | L2 卡跨项目复用（承接 D4 暂缓的共享知识） | 第二个项目能检索到第一部的方言卡 |
| P5 推广 | 用同一张五项表接入第二个工艺维度（建议钩子或情绪节奏） | 不改工具，只加卡和文档 |

P0 先行：先证明“正例进包、单独一遍、单独一读”确实让编剧更愿意选新版，再写工具。P0 结果不成立时，停下来重看成因，不进入 P1。

## 7. 待定

- 声音卡例句由编剧写，还是 AI 起草、编剧改：影响 P0 的工作量。
- 台词遍是否默认换模型：取决于评测结果和成本。
- 工作室知识库放在哪（本地目录还是 mali-story）：与 D4 的共享知识决定一起定。
- 人工改动率需要编剧在 mali-story 页面上改稿；若仍在飞书或 Word 里改，要先解决回流。
