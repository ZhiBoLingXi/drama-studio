# 台词库产品设计

日期：2026-10-12 · 状态：产品设计提案，未实施 · 上游：[工艺闭环设计](drama-studio-craft-loop-design-2026-10-10.md)、[知识设计](drama-studio-knowledge-harness-design-2026-09-29.md)、[系统架构 v1.2](drama-studio-system-architecture-2026-09-29.md)

## 1. 要解决什么

AI 写的台词不像人说的话。已经验证过的解法是给它人写的本剧正文（见工艺闭环设计第 8 节）。但这个解法有三个缺口：

- **新项目没有人写的正文。** 开新剧时声音卡只能由 AI 自己编例句，正是效果最差的做法。
- **经验留不下来。** 主创在一部剧里给的正文、改句、意见，下一部剧用不上。
- **来源单一。** 一个人物该怎么说话，除了本剧正文，还可以参考同方言、同年代、同类人物的真实说法，现在没有地方放。

台词库就是补这三个缺口的：把各种来源的“人怎么说话”存成可检索的材料，在写人物、写正文、改稿时按需要取出来放进上下文。

**不做的事：** 不是把整部剧本塞进上下文的检索系统；不训练或微调模型；不自动判断台词好坏；不替代本剧正文（有本剧正文时它永远优先）。

## 2. 谁用，怎么用

| 角色 | 想做的事 | 在产品里怎么做 |
| --- | --- | --- |
| 主创（编剧、导演） | “把我这部剧加进库”“这句不对，应该这么说” | 给文件或贴改句，其余由 AI 整理；看库的目录页 |
| 主创 | 开新剧时让人物说话有根据 | 说明地域、年代、人物类型，AI 从库里取材起草声音卡 |
| AI 作者（Codex、Claude Code） | 写某一集时拿到对口的例句 | 按本集出场人物、关系和意图检索，装进作者包 |
| 工作室负责人 | 知道库里有什么、缺什么、哪些来源能用到什么程度 | 目录页、来源清单、权利标注 |

## 3. 通用做法：一条管线，五种来源

不为东北话、年代剧或某个题材做专门功能。所有来源走同一条管线，差别只在权利等级和标注。

```
采集 → 切分 → 标注 → 提炼成卡 → 检索 → 进包使用 → 反馈 → 治理
```

### 3.1 来源与权利

每份来源入库时定一次权利等级，它决定这份材料能用到什么程度：

| 来源 | 例子 | 权利等级 | 能怎么用 |
| --- | --- | --- | --- |
| A 自有正文 | 工作室编剧写的剧本 | 自有 | 学说法，可在本工作室的项目里引用原句 |
| B 主创改句 | “AI 原句 → 改句” | 自有 | 同上；同时是反例来源 |
| C 对标作品 | 拉片得到的逐集转写 | 仅参照 | 只学说法和结构，不复用原句；成稿要做重合检查 |
| D 公开语料 | 方言词典、口述史、公开访谈、公开帖子 | 仅参照，或按来源许可 | 取词和说法；整段对话不入库 |
| E 采风与口述 | 主创访谈、田野笔记 | 自有或按约定 | 学说法；涉及真人时去掉可识别信息 |

规则：

- 权利不清的按“仅参照”处理。
- 私人聊天记录、未公开的个人对话不入库。公开内容里的人名、账号、联系方式在切分时去掉。
- 第三方来源的原句在卡上标“不可照搬”，对应知识卡的 `transfer.notTransferable`。
- 分发的技能包里只放合成例子；任何真实来源只留在项目或工作室的库里（沿用现有规则）。

### 3.2 三层对象

| 对象 | 是什么 | 多大 | 进不进上下文 |
| --- | --- | --- | --- |
| 来源 | 一份文件或一个网址：权利等级、日期、sha256、覆盖的集数 | 整份 | 不进 |
| 语料片段 | 一小段来回（1–6 句），逐字保留，带标注和出处 | 几十到两百字 | 一般不进，供提炼和抽查 |
| 说法卡 | 从若干片段提炼：什么处境、怎么说、3–8 句例句、反例、不适用的情况 | 三五百字 | 进，是检索和装包的单位 |

另有两种已经存在的卡，放在同一个库里：**声音卡**（某个人物怎么说话，属于项目）和**对照卡**（AI 原句与改句）。声音卡可以由说法卡组合出来：方言与年代的说法，加人物类型，加关系模式，再加这个人物自己的口头禅。

说法卡沿用 `knowledge-card`（`K5`）；片段和来源是新对象。

### 3.3 标注：按维度，不按清单

用开放的维度描述一段话，而不是预先列好方言或题材的清单。这样换任何地域、年代、题材都不用改产品。

| 维度 | 说明 | 例 |
| --- | --- | --- |
| 地域 | 方言或口音区 | 东北、川渝、粤语区、无明显方言 |
| 年代 | 故事年代 | 八十年代、当代 |
| 说话人 | 年龄段、身份或职业、性格倾向 | 中年、村干部、嘴硬 |
| 对谁说 | 关系与上下位 | 对配偶、对长辈、对对手、对陌生人 |
| 意图 | 这句话在干什么 | 求、拒、损、哄、试探、炫耀、认错、施压、打岔 |
| 情绪强度 | 低、中、高 | |
| 题材与媒介 | | 年代轻喜剧，短剧 |

每个维度有一小组推荐取值，允许自由填写；目录页会列出实际用到的取值，同义的由人合并。标注由 AI 起草。自有来源的标注直接生效，第三方来源的卡默认只作参照。

## 4. 功能

### 4.1 入库

主创说“把这部剧加进台词库”或给一个文件、链接：

1. 问一次权利等级（自有、仅参照、公开许可），记录来源。
2. 按集、按场切分，抽出来回片段；去掉可识别的个人信息。
3. AI 给每段标注，并把相近的片段提炼成说法卡，例句逐字取自片段并带出处。
4. 给出入库报告：多少片段、多少卡、覆盖了哪些地域、人物类型和意图，哪些没标上。

从互联网采集由宿主用它自己的联网能力完成，产物是和上面一样的文件，再走同一条入库流程。随包的本地工具不联网，这一点不变。

### 4.2 开新剧时起草声音卡

C2 写人物小传时：

1. 按人物的地域、年代、身份、主要关系到库里检索说法卡。
2. 用检索到的材料起草声音卡。例句的来源写清楚：取自本工作室的哪部剧，或是参照哪类来源后新写的。
3. 库里没有对口材料时如实写“无库内依据，AI 起草”，并把这个缺口记进目录页。

### 4.3 写正文与改稿时检索

装作者包和台词包时，按本集的出场人物、两两关系和集纲里的意图检索：

- 优先级：本剧人写正文里的原句，其次本剧声音卡，再次工作室库里的说法卡，最后是技能包自带的通用卡。
- 预算：知识分区不超过包的四分之一。
- 多样性：同一张卡、同一句例句不连续多集出现，避免全季复读同一句口头禅。
- 检索由脚本按标注和关键词过滤，从过滤结果里选哪几张由模型决定。脚本不做语义判断，也不联网。

### 4.4 反馈回库

- 主创贴改句：存成对照卡；被否的 AI 句进相关声音卡的反例；改法有普遍性时提炼成一张待确认的说法卡。
- 台词读标出的问题和采纳的改法：定稿后同样处理。
- 每张卡记录被装进过哪些集的包。主创对某几集不满意时，可以查到那几集用了哪些卡。

### 4.5 目录页

一页可读的目录，主创和负责人不用看 JSON：

- 有哪些来源，各自的权利等级和入库日期。
- 按地域、年代、人物类型、意图列出卡的数量，标出空白。
- 最近新增、最常被用到、被主创否过的卡。
- 记录在案的缺口，如“某方言的长辈对晚辈没有材料”。

### 4.6 治理

- **防照搬**：成稿与“仅参照”来源做字面重合检查（现有 `dup-check`），超过阈值的句子列出来改。
- **退役**：被否的卡标 `retired`，不再进包；引用过它的集可以查到。
- **权利复查**：来源的权利等级变了，它派生的卡跟着变。
- **去重**：同一来源重复入库按 sha256 识别。

## 5. 放在哪

按已有决定先放本地，分三层，检索时由近到远：

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 项目库 | 项目目录 `knowledge/` | 本剧的来源、片段、声音卡、对照卡 |
| 工作室库 | 工作室设置里指定的本地目录 | 跨项目复用的来源、片段和说法卡 |
| 随包通用卡 | 技能包 `references/` | 只有合成例子 |

工作室库是新增的，需要放开知识卡现在被禁用的 `scope.level: studio`。项目收尾时，把项目库里权利为“自有”的来源和卡提升到工作室库，由主创确认一次。

以后迁到 mali-story 时，页面做正本，本地做缓存，和正文的做法一致。迁移不改变上面的对象和流程。

## 6. 衡量

| 指标 | 怎么得到 | 说明 |
| --- | --- | --- |
| 有依据的声音卡比例 | 脚本统计：例句有库内出处的声音卡占比 | 衡量库有没有被用上 |
| 检索命中 | 脚本统计：每集装进了几张库内卡，多少次检索为空 | 衡量覆盖 |
| 台词读标出的句数 | 审读记录里统计，按集比较 | 间接的质量信号，不单独当结论 |
| 主创盲选 | 同样几集，带库和不带库各出一版，不标来源 | 唯一直接的效果证据 |
| 字面重合率 | `dup-check` 对“仅参照”来源 | 必须保持在阈值以下 |

脚本只负责前两项和最后一项的统计。库有没有让台词变好，以主创盲选为准。

## 7. 分期

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M0 最小可用 | 来源与片段两种对象；标注维度；放开工作室级；从一份自有正文入库；目录页 | 用已有的一部剧的人写正文入库，得到片段、说法卡和目录页；重复入库不产生重复 |
| M1 用起来 | 检索按标注过滤；C2 起草声音卡时取库内材料；装包的优先级与多样性规则；卡的使用记录 | 一个没有人写正文的新项目，声音卡的例句都有出处或写明“无库内依据” |
| M2 验证 | 同样三集，带库与不带库各一版，主创盲选 | 带库版被选中的比例；不成立就停在这里重看 |
| M3 第三方来源 | 对标作品转写入库（仅参照）；成稿对库的重合检查 | 重合检查在夹具上可复算 |
| M4 公开采集 | 方言、年代的公开材料采集规范与入库 | 采集到的文件走同一条入库流程 |
| M5 上云 | 迁到 mali-story，网页上看目录 | 本地与远端内容一致 |

M2 是关口：自有来源的库如果在盲选里没有帮助，就不做 M3 之后的采集。

## 8. 风险

| 风险 | 对策 |
| --- | --- |
| 照搬别人的台词 | 第三方来源只作参照；卡上标不可照搬；成稿做重合检查 |
| 隐私 | 私人对话不入库；公开内容去掉可识别信息 |
| 库越大越杂，检索出不对口的材料 | 权利与来源优先级固定；卡要有出处和不适用情况；被否即退役 |
| 口头禅和方言被用滥 | 多样性规则；台词读专门标“学过头” |
| 通用材料盖过本剧特色 | 本剧人写正文永远优先，库只在没有时补位 |
| 标注全靠 AI，错了没人知道 | 目录页列出标注取值供人合并；卡的使用记录让问题能追到卡 |
| 维护成本 | 入库和提炼由 AI 做，主创只做权利确认和抽查 |

## 9. 待主创决定

1. 对标作品的转写能不能作为“仅参照”来源入库。这决定 M3 做不做。
2. 第一份入库的自有正文用哪部剧。
3. 工作室库放在哪个本地目录，谁可以往里提升材料。
4. M2 盲选由谁来选，选几集。
