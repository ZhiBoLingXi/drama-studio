## 1. 架构结论

采用“可替换 AI 宿主 + 模块化创作领域组件 + 有来源的知识供给 + 单一权威项目服务”。

- 六个小 Harness 是六种创作责任，不是六个常驻 Agent、六个服务或六份相互独立的故事记忆。
- Drama Studio 定义创作过程、上下文规则、领域交接和确定性检查；宿主承担模型调用与通用工具执行。
- Mali Story 持有正式项目、采用、权限和远端任务权威；本地保留候选工作区与运行证据，不复制正式采用权。
- 知识按来源、允许用途、适用条件和版本管理；“存在于库中”不等于事实正确、方法有效或本剧必须采用。
- 以不可变创作产物与显式依赖连接模块。聊天历史、摘要、模型的自述都不是唯一状态源。

系统不是固定流水线，也不是自由聊天。它允许探索与返修，但任何会影响后续的选择都要变成可交接产物。

### 1.1 前案还缺少的架构闭合点

前案已定义功能和知识类型，但还需要明确：

1. 六模块访问的“人物”和“剧情事实”是否来自同一版本。
2. 谁判断需要什么知识，谁保证引用、权限和信息身份正确。
3. 正文发现集纲不成立时，怎样返回上层而不产生第二套剧情。
4. 候选状态怎样影响后续，又怎样不污染正式事实。
5. 新知识、旧知识失效、前文修改，对哪些产物产生影响。
6. 何种并行是安全的，什么证据才允许整合与采用。

只拆提示词或 Agent 不能解决这些交界问题。这是架构层面的缺口，不等于已经证明它们是每次创作失败的唯一原因。

## 2. 设计驱动与不承诺事项

| 用户面对的问题 | 对架构的要求 | 架构本身不能保证的部分 |
| --- | --- | --- |
| 人物像标签，台词不像本人 | 原场面、关系策略、所知边界可恢复；人物模型可随经历更新 | 生成器一定能写出好台词 |
| 情绪平、只会解释 | 集纲交付选择与变化依据；正文实现；审读可退回上游 | 情绪机制对每个观众都有效 |
| 连贯性差 | 正文来源、计划、候选、状态索引分离；版本与依赖有效 | 自动发现所有隐含文学联系 |
| 剧情同质化 | 多源生活材料、条件性方法、角色化检索、因果比较、自我重复记录 | 全网原创或必然创新 |
| 写长就失忆 | 外置项目状态、可回读原文、稳定交接、跨段落整合 | 一个摘要能无损代替全剧 |
| 修改引发连锁问题 | 显式变更提案、影响分析、过期标记、重新核对 | 所有修订能自动合并 |
| 测试通过但导演不能做 | 工程、创作、真人采用、制作证据分开 | 没有真实条件也能承诺制作成功 |

非目标：重建通用 Agent runtime、第一版即拆微服务、模型评分自动采用、全网采集、自动付费制作、新建完整编剧 UI、以知识库替代主创取舍。

## 3. 逻辑架构与部署边界

```text
用户／主创／编辑／导演
        │ 任务、限制、反馈、针对版本的决定
        ▼
AI 宿主：对话、模型执行、工具调用、实际 session
        │
        ▼
┌──────────── Drama Studio 领域组件 ────────────┐
│ 任务与依赖协调：范围、下一动作、有限返修、接续 │
│                      │                       │
│ 上下文构建器 ←→ 知识定位与适用性选择          │
│        │                                     │
│ C1 定位 → C2 人物世界 → C3 结构 → C4 集纲     │
│                                      ↓       │
│                      C6 审读整合 ←→ C5 正文   │
│        ↑        显式变更提案与影响范围        │
│ 产物登记／运行记录／版本与权限检查             │
└──────────────────┬───────────────────────────┘
                   │ 明确的读写适配接口
        ┌──────────┴─────────────┐
        ▼                        ▼
本地候选／知识工作区       Mali Story 权威服务（MCP）
显式目录、单写者首版       正式项目／采用／权限／任务
                         候选与来源的既有持久能力

知识来源：项目私有／工作室授权共享／允许使用的公共材料
评估资料：独立用途域，不进入常规创作检索
```

图中是逻辑边界，不是一组件一进程。Drama Studio 首版保持可安装、内部模块化；远端复用现有服务。知识读接口可以接本地文件，确需云共享时再由有权限的共享存储适配，不能用一个“公共假项目”绕过项目隔离。

“任务与依赖协调”只规定领域动作和允许的转换，不负责建设通用任务调度器、模型网关或新的多 Agent 框架。

## 4. 组件所有权：谁读、谁产出、谁无权决定

| 组件 | 责任 | 允许产出／写入 | 禁止越界 |
| --- | --- | --- | --- |
| 任务与依赖协调 | 恢复目标、范围、输入版本；决定可执行步骤与缺口 | 任务记录、执行计划、返修任务、运行状态 | 根据模型建议伪造用户同意、无限扩大任务 |
| 上下文构建器 | 识别所需资料；按角色组装确定版本的工作包 | ContextSnapshot 与选材记录 | 自动把选入资料提升为本剧事实 |
| 知识供给 | 来源读取、定位、条件性知识、用途过滤、相似结构线索 | 知识修订、检索结果与缺口 | 擅改人物、替用户决定创作方向 |
| C1–C5 创作工位 | 在指定问题、材料和空间内创作 | 完整候选产物、状态变化提案、上游变更提案 | 直接更新正式正文和正式连续性 |
| C6 审读与整合 | 阅读正文、核对证据、定位问题所在层、比较收益与损失 | 审读记录、整合候选、返修建议 | 把评分当采用；以作者解释代替正文效果 |
| 产物与运行登记 | 不可变版本、依赖、请求身份、实际结果及恢复 | 候选记录、历史审读、运行回执 | 把“运行完成”改写成“创作目标完成” |
| 正式采用服务 | 校验真实权限、决定、目标版本与当前项目版本 | 正式采用记录及对应的持久更新事件 | 由生成模型直接越过采用接口写正式块 |
| 评估能力 | 用隔离材料检验写作、审读及流程 | 指定方法版本的评估证据 | 将保留题答案回流给普通作者上下文 |

组件间传递产物引用和明确接口，不传“你应该还记得之前说过……”这样的隐含依赖。

### 4.1 执行层级：哪些约束真能被强制

宿主模型通常能直接读写工作目录，上表的“禁止越界”只有落到代码或服务端才是边界。每条不变量必须标注执行层级：

- **S 脚本强制**：随包 Python 工具拒绝或报错，有正反测试。
- **R 服务端强制**：mali-story 鉴权、版本比较或幂等键拒绝。
- **M 模型约定**：写在方法文档里，由模型遵守；只能用审读或抽查发现违反，不能阻止。

| 不变量 | 层级 | 落点 |
| --- | --- | --- |
| 正式采用只经有权接口、核对目标版本与当前权限 | R | mali-story Adopt 路径；Brief 批准追加语义 |
| 同一请求身份不同输入即冲突；断线后可对账 | R | StoryArtifactService 请求身份与修订契约 |
| 候选保存不等于采用 | R | 候选与采用是不同接口和记录 |
| ContextSnapshot 引用的版本存在、未混版、超预算不静默截断 | S | `scripts/context` 组装与引用核验 |
| 知识卡的允许用途与项目范围在装包时过滤 | S | `scripts/knowledge` 过滤；仅对经工具装包的材料有效 |
| 评估保留题不进入创作包 | S＋M | 工具不装入；但模型仍能直接读文件，故评估声明须按 §13.3 降级 |
| 工位只写本层候选、不改正式正文与连续性 | R＋M | 远端由采用接口保证；本地文件只能靠约定 |
| C6 首读不看作者解释 | M | 审读方法；无独立上下文时如实记为串行自评 |
| 状态变化与计划偏差以提案形式上报 | M | 工位方法与输出模板 |
| 用户决定不能由模型填写代替 | R＋M | 远端验证身份；本地“已批准”字段不构成认证 |

规则：D0–D5 的验收条件只能引用 S 或 R 项；M 项以审读记录、抽查样本和发现的违反次数报告，不写成“已保证”。新增不变量时先定层级，定不下来就按 M 处理。

## 5. 一个小 Harness 的内部契约

一个 Harness 至少由以下部分组成，而不是一段角色提示词：

1. **责任与决定**：本层要解决的问题，哪些属于上游、哪些留给下游。
2. **输入契约**：允许的产物类型、版本、状态、缺口及授权范围。
3. **上下文配方**：必读本剧依据、可选知识、角色可见性、信息预算与遗漏策略。
4. **创作方法**：产生和选择方案的办法；保留探索空间，不把方法变成固定剧情格式。
5. **输出契约**：完整可读产物、少量交接元数据、待核状态与变更提案。
6. **审查与返修**：针对本层目标的判断，修本层还是返回上游，迭代上限。
7. **运行协议**：实际输入、方法版本、结果位置、中断状态和下一动作。

这些部分独立版本化并共同记录于一次运行。修知识卡不必重写整个 Harness；修上下文配方不应悄悄改变任务范围；换模型不应改变正式采用权限。

### 5.1 六个工位的交接对象

| 工位 | 要作出的决定 | 主产物 | 对下游的必要交接 |
| --- | --- | --- | --- |
| C1 创作定位 | 写谁的什么困境，提供什么体验，独特性在哪 | 选题候选／创作简报 | 类型承诺、核心矛盾、创作立场、明确限制、选择状态 |
| C2 人物与世界 | 人物如何争取、如何冲突，规则怎样产生代价 | 人物与世界包、声音探针 | 欲望／顾虑／策略、关系、能力边界、已选与待探索内容 |
| C3 全剧与段落结构 | 选择如何造成下一段，结局怎样由前文生成 | 因果主线、人物弧、段落结构 | 关键承诺、回收、不可逆选择、季间约束、可调整接口 |
| C4 分集集纲 | 本集谁怎样改变局面，留下什么后果 | 可写的分集纲 | 入口、行动目标、阻力、关键选择、关系变化、出口和待核前提 |
| C5 正文 | 人物此刻怎样做、怎样说、怎样影响对方 | 完整剧本正文 | 实际发生的事、计划偏差、所知与关系变化提案 |
| C6 审读与整合 | 哪些成立，哪里不足，应修哪一层 | 审读记录与整合候选 | 目标判断、证据、损失、未决项、返修归属和受影响范围 |

主产物可以是 Markdown 正文；结构化字段只负责交接，不把文学作品压成一张穷尽心理状态的表。简短选择说明用于记录取舍，不要求保存或展示模型内部推理过程。

工位完成、用户选择、正式采用是不同事件。不新增六次人工审批；继续遵守选题与送审包的既有审批及用户明确的修订授权。

## 6. 数据架构：三类主数据，四类关联证据

### 6.1 主数据

| 主数据 | 内容 | 权威来源 |
| --- | --- | --- |
| 项目内容 | 创作意图、设定、结构、正文、人物关系及事实 | 明确版本的项目产物；正式性来自真实采用记录 |
| 知识内容 | 原始材料、条件性方法、案例、表达样本、相似结构和反馈经验 | 精确来源、权限、证据性质和知识修订；没有统一“绝对正确”状态 |
| 方法配置 | 工位契约、上下文配方、创作／审读方法、适用条件 | 可版本化的 Drama Studio 方法包及项目覆盖项 |

### 6.2 关联证据

- **ContextSnapshot**：某次任务实际提供哪些版本、原文区间和知识；排序、分区、缺口和预算处理。
- **ModuleRun**：任务、实际上下文、方法版本、宿主／模型可知信息、实际结果、错误及恢复点。
- **ReviewRecord**：对哪个产物和目标的判断，实际阅读范围、评审上下文、事实／目标／偏好及证据。
- **DecisionRecord**：谁通过何种真实交互，对哪个版本、哪些范围作出什么决定。

### 6.3 最小关联图

```text
原始来源版本 → 证据片段 → 知识修订
                               │
项目产物版本＋方法版本 ─────────┤
                               ▼
                       ContextSnapshot
                               ↓
                          ModuleRun
                               ↓
                       新的产物版本
                         ↙          ↘
                   ReviewRecord   下游依赖
                         ↓
                   DecisionRecord
                         ↓（正式权限与版本核验）
                    已采用项目版本
```

关系可以先用引用表和文件 manifest 表达，不因此必须引入图数据库。

每个引用至少能说明对象、修订、来源位置和所属范围。相同正文哈希只说明内容相同，不代表相同授权、业务操作或采用事件。

### 6.4 本剧记忆是可回读的派生视图

人物所知、伤势、物件、承诺、关系余波等是正文的带来源索引。正式事实由已采用正文及其采用决定确定；候选可以产生独立的分支事实视图。

不允许三个来源平级竞争：

- 集纲说明准备发生什么。
- 正文说明该版本实际写了什么。
- 状态索引帮助定位正文，但不覆盖正文。

发现矛盾时保留冲突及两端引用，不让模型挑方便的一端。创作意图与正文偏差也应报告，不能以“正文优先”抹去用户明确要求。

### 6.5 状态必须分维度

运行是否结束、输入是否新鲜、阅读是否覆盖、创作目标是否达成、用户是否采用、制作证据是否充分分别记录。不存在一个能够代表全部意义的 `quality_passed` 或 `done`。

## 7. 上下文架构：语义选择与确定性组装分开

这是系统的核心协作点，不是一个向量检索函数。

### 7.1 请求形态

概念上的 `ContextRequest` 包含：工位、具体创作问题、项目／分支／版本、读取范围、写入范围、必需依赖、信息可见性、知识缺口、来源权限与排除项、预算、方法版本。

读取范围可以大于写入范围。例如只改第21集，可以读取第20集与后续承接，但不能因此获得修改它们的权限。

### 7.2 两个协作部分

| 部分 | 做什么 | 如何避免自说自话 |
| --- | --- | --- |
| 语义选材 | 判断本轮在作什么决定、缺哪种资料、哪些原场面与知识相关 | 给出简短选材理由和缺口；允许“无需共享知识”；保留实际材料供回读 |
| 确定性组装 | 读取固定版本、核对引用与访问范围、去完全重复、保留身份和区间、检查预算 | 超量不静默截断；错版不混包；来源缺失不伪装齐全；保存实际包 |

模型建议“需要这个事实”不证明事实存在。确定性工具证明引用确实存在，也不证明引用真的支持语义结论；两种证据分别评价。

### 7.3 组装过程

1. 读取确切任务、项目版本和工位配方。
2. 按权限与用途过滤可访问来源；精确加载必要依赖，不把关键前文交给相似搜索碰运气。
3. 恢复本剧原场面及状态，区分世界真相、人物相信、观众已知与未来计划。
4. 语义层提出缺口和可选知识；定位服务提供候选证据，允许多次有限展开。
5. 复核适用条件、同源重复、材料集中程度及相似情节风险，保留本剧自己的声音与创作立场。
6. 组装工作包；先保必要原文和任务，再处理可选材料。放不下就缩小工作单元或显式分阶段读取。
7. 固定快照并登记实际输入。执行期间追加材料必须登记新的展开记录或快照，不能沿用旧包宣称输入未变。

重现上下文不等于重现模型输出。宿主发生自动压缩或存在不可见上下文时，记录可知范围及局限，不声称完全隔离。

### 7.4 不同角色使用不同视图

- 作者视图：允许知道未来计划以便铺垫，但明确角色尚不知道什么。
- 读者效果视图：只给该阅读阶段可见正文及必要前文，不先给作者解释和结局。
- 事实审查视图：允许展开更远的前后文，核对两端与反证。
- 相似性审查视图：可访问对照作品和结构索引；返回具体风险，不默认倒灌整套对照剧情给作者。
- 评估视图：保留题、参考答案与其派生版本按用途隔离，不参与普通创作检索。

这些视图首先是信息契约。若宿主仍能任意访问同一文件系统，不能声称具备安全沙箱式隔离。要求强隔离时必须使用受限工具、权限域或实际隔离执行环境；只写“不要读取”不是访问控制。

## 8. 知识架构：证据、方法和创作启发不能共用一种权威

知识类型沿用 K1–K9；本节规定它们如何被管理和消费，而不重复列九个数据库。

### 8.1 两条生产路线

**外部材料路线**：获准来源 → 精确证据 → 观察与解释分开 → 条件性知识／案例 → 适用性复核 → 可检索。

**创作反馈路线**：固定输入与前后产物 → 实际审读／用户／制作反馈 → 收益和损失 → 经验候选 → 有条件复审与复用。

两条路线共用来源和权限契约。反馈路线不能仅由生成器自评完成；没有独立或真人反馈时如实记录，仍可保留启发性假设，但不能标为已证实规律。

### 8.2 知识条目的三个独立状态轴

- 加工状态：原始、待整理、已整理、已修订／退役。
- 证据性质：材料观察、来源陈述、解释、创作假设、合成示例；可另记核验结果和冲突。
- 允许用途：项目私有、工作室共享、公共授权，以及创作参考／比较专用／评估专用等限制。

共享知识不能自动进入任何项目的设定。项目采用一个虚构设定，也不能把它升级为真实世界知识。

### 8.3 反同质化应分布在三个组件

- 知识供给：保留不同来源、生活处境、机制和反例；转载不伪装多源，不按流行度垄断材料。
- 创作工位：差异必须进入利益、选择、代价和解决路径；具体情节不被抽象方法悄悄夹带。
- 审读整合：比较已读作品和自身历史的关系功能、事件排列及解法；回到原文确认风险。

不做统一“新颖度越高越好”优化。类型承诺、熟悉感、人物一致性与新鲜感可能冲突，由本项目目标决定取舍。

### 8.4 知识更正与撤回

知识普通更新不应使所有使用过旧版本的剧本自动失效；历史运行仍真实使用过旧知识。

- 方法新增另一种写法：供未来选择，不自动重写旧稿。
- 来源事实被纠正：定位依赖它的产物，标记待核并分析实际影响。
- 访问权被撤回：限制原文、摘要、派生卡及受影响快照的继续访问，按实际保留要求处置；不能借不可变历史绕过撤回。
- 无法确定派生影响：标 unknown，扩大复核范围，不编造完整血缘。

### 8.5 首版范围：只做项目私有知识

mali-story 的 `CreativeMaterialRef` 目前只接受 `story_artifact` 与 `episode_candidate`，没有知识条目类型，也没有跨项目授权模型。因此：

- D0–D3 的知识卡只存在于单个项目的工作目录，允许用途只有“本项目创作参考／比较专用／评估专用”。
- “工作室共享”和“公共授权”两个范围保留在契约里，但在 D4 之前不实现、不装包。
- 跨项目共享需要先定义所有者、授权与撤回的服务端落点（§12 KnowledgeRead 的远端适配）；不用本地共享目录或“公共假项目”代替。

## 9. 运行与返修：一次调用的完整生命周期

正常路径：

1. 宿主提出范围明确的任务，协调组件检查授权与输入。
2. 固定项目／分支基线，构建并登记上下文。
3. 宿主调用对应工位方法，模型产生候选。
4. 保存原始候选和运行回执；格式问题与创作问题分开，不丢弃失败结果。
5. 提取状态变化与计划偏差提案，保留原文依据。
6. C6 审读形成问题与目标判断，协调组件选择允许的定向修订或交付。
7. 新修订保留父版本和实际影响；超出授权或涉及上游方向时提出变更，不静默执行。
8. 用户／有权主体对明确版本作出决定；只有相应正式接口可以更新正式状态。

每次运行的读取依赖固定；返修创建新的运行与修订。项目层面允许反复迭代，但单次运行的依赖图不靠互相等待的循环节点表达。

### 9.1 上游变更提案

`ChangeProposal` 至少说明：当前产物、问题证据、建议变更、被触及的上游决定、已知影响、未知范围、保护项损失、需要的决定。

它不是自动改写命令。协调组件依据既有任务和用户权限判断：可局部修复、可在已授权范围探索、需要确认方向、或只能报告。

有限返修预算属于本轮任务；触顶可以交付未达目标的候选及瓶颈，不能改判标准使它“通过”。

## 10. 并行、一致性与恢复

### 10.1 两种依赖要分开

- **执行依赖**：这一任务开始前必须具备哪些产物，例如写正文需要可消费的本集纲。
- **内容依赖**：这一段戏依赖哪些选择、信息与后果，前文变更会使其待核。

执行依赖满足不证明全部内容依赖已识别。两者的覆盖范围分别记录。

### 10.2 允许的并行

共享同一硬约束和事实快照的不同候选可以并行；素材整理与独立核验可以并行；接口稳定的相对独立段落可以并行。

强依赖集优先顺序完成关键决定；若先按计划接口并行写作，只得到推测性候选，必须与前集实际正文整合后才能成为一致的交付版本。

同一项目多个作者不能最后写入者覆盖前一个。用预期修订／分支头比较拒绝冲突，保留双方产物，重新读取再决定。

### 10.3 本地与远端权威

mali-story 的 StoryArtifactService 已有快照绑定、候选保存回读、请求身份与修订契约。本地不重新实现这些能力。

| 数据 | 存放位置 | 本地需要实现的只有 |
| --- | --- | --- |
| 候选产物、修订、采用决定 | mali-story | 调用适配与回执记录 |
| 知识卡与原始证据（项目私有） | 项目工作目录 | 文件读写、哈希、用途过滤 |
| ContextSnapshot、选材记录 | 项目工作目录 | 写入后不再修改的文件＋哈希清单 |
| 离线降级草稿 | 项目工作目录 | 文件＋父版本哈希；不做 CAS、幂等或多写者合并 |

- 离线模式是降级：没有 MCP 或断网时可以继续写草稿，每份草稿记录其依据的远端版本（或“无远端”）。联网后作为新候选提交，由服务端判断冲突。
- 离线选择的“当前稿”不是远端正式采用，绑定的远端状态只能标缓存及日期。
- 本地只支持单写者，不声称多主机协作。发现父版本哈希与远端当前版本不一致时，只报告冲突，不在本地合并。
- 联网模式采用状态以服务端回执为准。本地与远端 ID 显式映射，不因同名或内容相同就认作同一业务事件。
- 已确认（2026-09-29）：没有长期离线用户，不做本地完整版本管理。降级草稿只覆盖临时断线或 MCP 暂不可用。
- 服务端跨请求状态保存于共享存储，不能依赖某一副本内存。正式采用与其记忆更新事件需要可靠提交边界；派生索引允许异步重建，但未就绪必须可见。
- 关键索引未就绪时，可在原文读取范围确实充分的情况下直接核对；不能假装过期索引可用，也不能仅凭读取全文的声明证明理解。

### 10.4 幂等与未知结果

持久化操作使用稳定请求身份与输入指纹；同键同输入可对账，同键不同输入冲突。

这不等于模型调用恰好一次。模型或远端任务响应丢失，先查实际任务与回执；无法确认则标未知，由授权和预算决定是否重试，不能擅自假定未计费。

候选写完但前文已变化时，可以保存为过期来源候选，不能谎称当前有效。正式采用前必须重新核对目标版本、项目状态和当前权限。

## 11. 质量架构：记录可判断的证据，不设自动优质裁判

四类证据并列存在：

1. 结构与客观约束：格式、引用、版本、明确设定矛盾。
2. 创作目标：具体人物行为、对白、因果、情绪与辨识度。
3. 阅读与审美判断：判断者、目标读者、实际阅读范围、喜欢与不喜欢的依据。
4. 制作证据：具体团队、版本、片长／调度／资产条件与实际结果。

模型审读可以提出强有力的编辑意见，但不是事实证明或用户采用。程序可以证明引文存在，不能证明引文支持审美结论。

首次效果阅读不提供作者解释；之后再核对目标、原文和约束。不能把作者与评审都收到同一“应当感动”的解释后得到的一致意见，当成无提示观众效果。

知识使用、工位选择、上下文和产物要能关联起来，以便区分：材料错误、选材缺失、方法不合适、生成实现失败、审读误伤、版本串线。诊断不能只输出一个总分下降。

## 12. 接口与既有实现的衔接

以下是逻辑端口，不是宣称已部署的新 MCP 工具：

| 逻辑接口 | 主要操作 | 所有权／适配原则 |

新增知识及工位元数据是否需要扩展持久 schema，必须逐对象验证现有载体与消费方，不把 JSON 塞进正文就宣布解决了类型、查询和权限。若需数据库变更，遵循迁移、snapshot、journal；本轮不改数据库。

## 13. 安全、可观测与架构验收场景

### 13.1 安全边界

材料中的指令、角色对白及知识卡内容都是数据，不能成为工具授权。权限过滤应覆盖原文、摘要、索引和派生材料；角色视图不取代服务端鉴权。

真实用户交互可以提供决定依据，但本地模型填写的姓名和“已批准”字段不构成身份认证。远端仍验证实际身份、对象与版本。

保留项目私密性；日志记录必要 ID、版本、状态及引用，私有正文展开受到同等权限控制。资料或授权撤回时，派生快照与备份也应纳入处置范围，具体保留策略待实际部署确定。

### 13.2 运行可观测

至少能回答：当前任务是谁提出的、使用哪版方法、给了哪些材料、遗漏什么、实际生成了什么、谁看过哪些内容、为什么返修、哪个决定仍未作出、下一步是否涉及外部副作用。

上下文可按权限重放；模型输出不保证重现。只有宿主提供真实模型／用量信息时才记录具体值，不能根据角色名或估算字数伪造 token 与费用。

### 13.3 用场景验证边界

以下是假设性架构测试，不是对当前剧本情节的事实描述。

| 场景 | 预期行为 |
| --- | --- |
| 第20集改为人物已知秘密，第21集仍按未知写 | 定位已知源依赖并标待核；回读所知与实际正文，不只更新摘要 |
| 正文为解决冲突新增了一项超出设定的能力 | 形成规则变更提案；不得自动写入世界事实并让后文默认成立 |
| 集纲没有设计情绪转折，只要求人物被感动 | C6 可返回 C4 的选择／经历缺口，不只让 C5 加哭泣或解释 |
| 知识搜索结果全是同一个套路的转载 | 来源谱系去重并披露集中；可补不同生活材料，不伪称多源支持 |
| 一个有效静场没有争吵和反转 | 不因缺少模板节拍自动判失败，按关系变化和本轮目标判断 |
| 两个 session 基于同一旧版本写了互不兼容结果 | 都保存候选，冲突整合；不最后写入者覆盖，不自动平均拼接 |
| 保存请求成功但客户端断线 | 用相同请求身份查询／重放结果，不创建重复采用事件 |
| 索引重建换了服务副本 | 从共享持久状态恢复；未就绪可见，不依赖原进程内存 |
| 审读模型能访问答案文件 | 不称保留题隔离成立；限制访问或降低评估声明 |
| 用户尚未认可、导演反馈缺失 | 保留候选及未知；可以继续独立离线工作，不自动扩稿或放行制作 |

这些场景通过只能证明边界行为。创作质量仍需实际正文与相应阅读证据。

## 14. 关键架构决策与取舍

| 决策 | 采用 | 未采用及代价 |
| --- | --- | --- |
| 系统形态 | 模块化领域组件＋可替换宿主＋既有权威服务 | 不做六个微服务；代价是逻辑边界要靠契约与测试维护 |
| 模块连接 | 版本化产物、依赖与变更提案 | 不以共享长聊天连接；代价是要维护交接和来源记录 |
| 知识组织 | 条件性知识、来源谱系、用途分域 | 不做单一热剧切片池；代价是需要持续知识编辑 |
| 上下文 | 模块专用配方＋语义选材＋确定性组装 | 不给所有模块同一个大包；代价是配方需分别验证 |
| 修订方式 | 局部返修可向上回传，保留版本与影响 | 不要求严格单向流水线；代价是协调与影响分析更复杂 |
| 并行 | 依赖明确后并行，候选隔离，实际正文整合 | 不全串行也不按集数均分；代价是需处理推测性候选 |
| 质量权威 | 多维证据＋主创／用户决定 | 不以总分自动采用；代价是仍需人作审美取舍 |
| 状态实现 | 内容修订、决定历史、可重建索引，复用现有可靠提交 | 不首版全量事件溯源／新工作流平台；代价是部分恢复与影响规则需显式实现 |
| 本地存储 | 候选与采用只存 mali-story；本地只放知识、快照和降级草稿 | 不在本地重建版本库；代价是离线期间无冲突检测，联网后由服务端裁决 |
| 约束执行 | 每条不变量标 S／R／M，验收只引用 S／R | 不把方法文档的“禁止”当边界；代价是部分约束只能事后审读发现 |

## 15. 需要确认与后续细化的边界

本稿建议采用上述逻辑架构。以下不影响先审查逻辑，但影响具体实现：

- 首个运行范围按本地单写者、私有资料、候选交付设计；若首版就要多人云共享，应提高权限与一致性要求并重新估算。
- 线上实际可用的读取、保存、采用接口，须通过真实能力发现验证；源码不代表部署。
- 工作室共享知识的管理者、可用素材权利、真人编辑责任，以及保留／撤回策略，需在接入真实资料前落实。
- 数字化的时长、预算、上下文容量和性能目标应来自真实任务与宿主，不在架构稿里捏造阈值。

### 15.1 共享知识的投入门槛

目前的依据只有第43–44集一次试验：每条件生成一次、同源模型评审、结果有分歧。K1–K9 的系统化生产代价高，不应先于证据铺开。

- D2 必须先跑“只用本剧分层上下文”（不加共享知识）的对照。
- 只有当对照显示本剧上下文的收益已经到顶、剩余缺口确属材料或方法缺失时，才扩大 K1–K9 的生产；否则优先改选材规则和工位方法。
- D1 的种子知识只服务 D2 的首轮问题，数量由问题决定，不为凑覆盖面整理。

### 15.2 成本构成

阈值不在此捏造，但每批交付要按以下构成报告实际消耗，用于 D1、D2 后的重估：

| 成本项 | 随什么增长 | 说明 |
| --- | --- | --- |
| 创作调用 | 集数 × 工位 × 候选数 | C4、C5 为主；多候选按倍数增长 |
| 审读调用 | 集数 × 审读轮次 | C6 至少两轮（盲读＋核对），相似性复核另计 |
| 返修调用 | 问题数 × 返修上限 | 由本轮返修预算封顶 |
| 上下文体量 | 必读原文＋知识卡 | 长篇后期前文增长最快，是缩小工作单元的主要原因 |
| 知识生产 | 条目数 × 人工核对 | 主要是编辑人力，不只是模型调用 |
| 人工等待 | 审批点与反馈轮次 | 两个创作审批点＋导演反馈，单独列出，不与机器耗时混算 |

只有宿主给出真实用量时才记录具体数值；否则记录调用次数与字数，标明为估算。
