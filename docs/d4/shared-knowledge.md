# D4-5 工作室共享知识：建还是不建（#48）

2026-10-08。**状态：主创 2026-10-08 确认“暂不建”。**本页只引用已入库的记录，不含正文。

> **2026-10-15 注（D6-5）**：语料缓存不属此决定。mali-story 官方模板语料的本地只读缓存是参考数据的缓存，不是知识卡，也不是共享知识；本决定（暂不建工作室共享知识）不因此重开。缓存放工作室级还是项目级是另一项待主创确认的事（[统一实施计划](../design/drama-studio-outline-dialogue-implementation-plan-2026-10-14.md) §8 #1），确认前放项目目录。

## 结论

**暂不建工作室共享知识。**

1. **没有增益证据。**唯一一次对照（D2）差异不明显，还带副作用；D3 不装卡也完成了全季精修和压缩，卡里那类规则由本剧的世界规则和修改单承担。
2. **共享会放大风险。**卡的失效条件是从单部剧里学来的（新设事实要给锚点、避免重复不能牺牲可见性）。跨项目共享时，适用条件更难核对，误用的成本会落到别的项目上。
3. **真正可复用的是方法，不是知识卡。**D3 能复用的是工位流程、契约、核对脚本，以及“修改单事实前提要核对”“保存要字节核对”这类做法。这些已经写进随包的方法文档（#26），不需要另建一套共享知识库。

## 成本与风险（如果现在建）

- **服务端要新增的东西**：mali-story 要有跨项目的知识存储，要有按团队划分的权限，卡的版本和退役状态要能被各项目的快照引用，还要有失效通知（某张卡退役后，各项目的 impact 能看到）。这些目前都没有。
- **drama-studio 侧要改的**：`knowledge` 命令要能读远端卡，`context-pack` 要支持远端卡引用，`impact` 要能跨项目定位影响。
- **风险**：在没有增益证据的情况下先建基础设施，之后很可能要推倒重来。

## 什么时候重新评估

满足任一条件就重开这个决定：

- 第二部剧在同类问题上复用了同一张项目卡，且有对照显示有帮助（N≥2，不同作者）；
- 主创或导演在两部以上的剧里反复给出同一类修改意见，而且这类意见能写成带失效条件的卡；
- mali-story 已经为其他原因提供了跨项目存储与权限，这时建共享知识的边际成本会显著下降。

在那之前，种子卡继续留在各项目私有目录，按需少量使用；`impact` 已能定位卡更正或退役的影响（#46）。
