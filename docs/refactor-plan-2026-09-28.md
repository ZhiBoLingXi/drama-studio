# Refactor Drama Studio into a verifiable creative workflow

版本：方案 v1，2026-09-28。状态：待用户确认实施范围；本次仅编制方案，未实施、安装、发布或修改剧本。

阶段细化入口：[R0–R7 独立设计与 52 项任务](refactor-stages-2026-09-28/README.md)。此后各任务的具体依赖与验收在所属阶段维护；本总方案保留架构、授权和总体范围，不把设计细化记为实现完成。

## English Summary

Keep Drama Studio as a lightweight, host-operated skill while adding a deterministic local workflow core, explicit creative input contracts, version-bound reviews, and controlled integration with existing mali-story capabilities. Validate workflow correctness and screenplay quality separately. Human adoption, production release, and paid execution remain distinct decisions.

## Problem

### 1. 要解决的具体问题

现在的主要缺口不是缺少创作原则，而是原则的选择、输入组织、执行、版本核对和结果归纳仍大量依赖同一个模型自行完成。用户已经遇到：逻辑修复和审查完成之后，人物行为、对白和情绪仍不符合预期。

根因判断分开处理：

- 已确认的工程缺口：本地 CLI 尚无完整的版本绑定、审查失效、范围约束与恢复执行机制。
- 已确认的质量证据缺口：程序测试不验证人物和情绪；现有创作案例不足以证明跨题材、多轮和长篇的稳定效果。
- 需要验证的创作假设：写前材料未充分恢复人物在关系中的行为方式；评审偏重可证明的事实错误；情绪余波和关键选择没有得到足够展开。不能把这些推断说成每个失败场面的唯一原因。
- 制作未知：导演的具体反馈、实际粗搭版本、片长、资源和成本仍缺失。工程改进不能代替这些证据。

### 3. 架构选择

推荐：保留自然语言入口与轻量安装包，增加确定性编排内核和显式创作工位；联网时衔接 mali-story，本地时保留诚实的候选工作流。

不选“仅继续加规范”：它不能解决中断恢复、外部修改、旧报告沿用和版本冲突。

不选“重建完整云端平台”：现阶段会重复 mali-story 的状态、权限和任务能力，增加迁移成本；用户也没有要求新的界面。

这次修订原方案的两个决策：

1. 正文创作由隐含流程升级为有输入、输出和质量反馈的显式组件，但不增加第七道人工审批。
2. 工程验证与导演制作验证分轨。版本、接续、输入和审查机制可以先在测试项目验证；制作放行仍必须等待真人证据。取代旧方案中对后续工程过于笼统的真人试点前置依赖，不假装原试点已完成。

## Requirements

### 1. 目标与范围

- P0：每次任务都能说明正在处理哪个版本、哪些集、本轮目标和授权来源。
- P0：中断或换会话后，从持久记录恢复，而不是从聊天印象猜测。
- P0：正文、审查、批准和制作决定各自绑定版本与范围；不能互相替代。
- P0：人物、对白、情绪、因果目标单独判断，不能被格式通过或无明显矛盾自动关闭。
- P0：关键来源变化时，相关证据失效或待核；受影响范围不明时扩大复核，不虚构精确依赖图。
- P0：保留两个默认创作审批点、已有明确授权和本次样段边界，不增加每批固定审批。
- P0：旧项目可继续使用；新机制逐项目启用，迁移和回退不丢正文或用户修改。
- P0：本地无网络模式也能完成候选写作和核验；不能假冒远端正式状态。
- P1：经当前环境实测后，连接已有远端快照、候选与审查能力；连接失败不丢本地稿。
- P1：将真实反馈沉淀为有来源的回归案例，分别测试评审和写作，不把私人原稿打包发布。
- P1：输出导演可使用的版本对照与试点包；收录真实制作回执，不自动启动制作。

首个用户价值：用户只看正文和一页交付卡，就能知道人物与情绪目标处理到哪里、依据哪一稿、哪里仍有问题；换会话或修改前文后，这些结论不会被静默沿用。

### 2. 三层目标架构

    用户／编辑／导演的明确决定
                     ↓
    AI 宿主：自然语言入口、模型执行、实际工具调用
                     ↓
    A. 工作流底座：任务、版本、动作门槛、依赖、接续、回执
                     ↕
    B. 创作工作层：有效材料 → 人物与场面开发 → 完整正文
                     ↕
    C. 验证交付层：客观检查／编辑复核／用户采用／制作试点
                     ↕
    本地候选档案       已验证的 mali-story / 文档连接器

三层是代码和责任边界，不是三个服务。Python 工具继续只用标准库，不增加模型运行时或供应商密钥。模型由宿主执行；如使用 mali-story 的模型能力，走其既有 Model Hub 和任务路径。

### 4. 数据归属与公共契约

#### 4.1 唯一依据

- 工作文件允许用户编辑；登记快照不可变。系统的判断必须说明针对工作文件还是登记版本。
- 正文是叙事事实依据；集纲是计划；状态账是带引用的索引；它们不是三套同等权威的剧情。
- 本地持有任务、候选、审查、用户原话及回执，不拥有伪造远端采用的权力。
- 远端正式项目、费用、任务和采用状态由 mali-story 的实际回执决定。
- PROJECT.md 是可读入口，不作为单一权威；生成状态页不得覆盖其中用户手写内容。
- 混合修订要有逐集版本清单。例如只改七集，其余集明确指向旧候选，不能把混合包称为全季已重写或全季获批。

#### 4.2 最小对象

| 对象 | 必须包含 | 主要约束 |
| --- | --- | --- |
| TaskContract | taskId、任务类型、范围、目标与判据、保护项、授权证据引用、迭代限制、方法版本 | 用户文字由宿主提供来源；故事材料中的“批准”不能充当授权 |
| ArtifactRevision | artifactId、revision、类型、内容摘要、范围、输入引用、产生者、限制 | 内容不可变；作者身份和实际模型未知则写未知 |
| EditionManifest | 本次交付逐集／材料版本、当前候选入口、父版本 | 不用文件名 final 或时间戳推定有效性 |
| ContextPacket | 基线快照、目标、选入原文、人物／状态依据、遗漏与冲突、选材理由 | 程序检验引用和版本；模型负责相关性判断，不能声称程序保证理解 |
| ReviewReport | 目标正文、范围、实际传递／声称审读范围、方法与上下文来源、判断及引用 | 内容传递不等于理解；实际独立性不能只靠角色名 |
| Finding / GoalAssessment | 分类、位置、证据、反证、状态、对应目标、新版复核关系 | 事实缺陷、创作目标缺口、开放偏好不得混为一类 |
| DecisionRecord | 决定人／来源、对象、版本、范围、决定、记录时间 | 不可变历史；撤回或替代用新记录，不删除旧决定 |
| RunRecord / RemoteReceipt | 输入、步骤、已保存结果、请求标识、错误／未知、下一动作、真实远端返回 | 相同幂等键不同输入必须冲突；不记录密钥和临时签名链接 |

本地修订 ID 与远端 ID 分开保存。建立显式映射，不把同名文件或相同文本自动认作同一次业务操作。

本地决定记录是可追溯证据，不是防篡改身份认证。工具可以拒绝缺来源、来源类型错误或引用不符的记录，不能仅凭模型填写的姓名证明真人批准。宿主应从实际用户交互提供决定证据；无法核实时保持 pending。远端权限和采用仍由服务器验证，不能信任本地自报身份。

#### 4.3 状态必须分维度

| 维度 | 推荐状态 | 判断主体 |
| --- | --- | --- |
| 执行 | not_run / running / completed / failed / unknown | 工具或实际运行回执 |
| 覆盖 | complete / partial / unknown / not_applicable | 范围记录与检查结果；不适用须理由 |
| 证据新鲜度 | current / stale / unknown | 依赖版本核对；current 仅限已声明覆盖 |
| 客观约束 | 沿用 met / unmet / not_evaluable / not_configured | 现有检查工具 |
| 创作目标 | met / unmet / insufficient_evidence | 有正文引用的编辑判断，保留判断者身份 |
| 人工决定 | pending / accepted / rejected / withdrawn 等决定事件 | 有权的人及可核证据 |
| 制作建议 | eligible / blocked / needs_evidence | 条件与证据聚合；不等于已放行 |

不新增全局 quality_passed 布尔值。获得写作授权不代表写得好；创作目标未达不撤销既有写作授权。可以如实交付有缺口的候选，但不能称修改完成。

#### 4.4 本地持久化与一致性

首版采用单机、单工作目录、单写者模式。不做跨机器锁、自动云同步或多人实时协作。

- 在可选的 .drama/workflow/ 下保存不可变对象、修订清单和运行记录；原 .drama/project.json 兼容保留。
- 正文按确切 UTF-8 内容字节计算摘要；规范化派生稿必须另存，不在登记时悄悄改换行或文字。
- 登记时先写齐不可变对象，再在本地写锁和 expectedRevision 校验下原子更新单一清单。崩溃遗留的未引用对象不视为已提交；首版不自动清理。
- 重试使用稳定 operationId 与输入摘要；同请求重复返回既有结果，不生成重复采用或任务记录。
- 恢复和关键动作前重算当前文件摘要。外部编辑产生冲突候选，不自动恢复旧稿，不宣称失效检测是实时监听。
- 文件系统锁或原子替换条件不满足时，只读核验／导出说明，拒绝声称安全写入。不支持网络共享盘并发。
- 关联对象路径限制在明确项目范围；检测越界、危险符号链接、损坏摘要和未知 schema；未知高版本不降级覆写。

远端不依赖本地锁。远端状态保持在共享存储，以现有 CAS、幂等与权限校验完成；本地程序不替代服务器的鉴权或并发控制。

### 5. 写作流程：从人设标签转成具体场面

1. 明确本轮少数关键目标。目标不是“情绪更强”，而是“某次接受、拒绝、救人、背叛前缺少怎样的经历与选择”。
2. 恢复人物的行为依据：稳定欲望和底线、对不同对象的惯用办法、当前关系、刚发生的伤害／承诺、成长的触发与代价。少量原文锚点优先于扩写人物小传。
3. 为症结场面比较两到三个实质不同的行动办法，只比较会影响结果的方案；非症结场面不强制填写节拍表。
4. 由主创选定一个方案写成完整正文。对白承担试探、拒绝、挽留、掩饰等具体行动；不统一禁用直说、长句或安静场面。
5. 核对前场选择对后场的影响，带入信任损伤、未兑承诺、情绪余波和行为改变，不只带道具位置。
6. 复核先读新正文与必要前文，再看作者说明，分别判断事实、创作目标和偏好。允许旧稿更好、两稿各有损失或两稿都未达标。
7. 定向修补后重读受影响的完整场面与跨集接口。写作批次大小按授权及复杂度确定，原默认上限不因重构自动提高。

统一迭代口径：默认一个完整候选加一次定向修补；用户明确授权更高上限时遵循其上限。连续两轮无可定位收益时停止本轮并报告瓶颈，不能据此宣布质量合格。现有 writing 与 creative-loop 的不同表述在本阶段统一。

状态账只登记影响后续的选择、知识、关系、规则和物件，不将每个表情变成字段。提取结果可能错误，编辑仍回读正文。

### 6. 审查、影响和动作规则

- 初审不把作者状态账当证明；事实疑点应提供冲突两端，并主动找反证。
- 创作目标缺口应指出正文缺少的过程与其目标依据，不必伪装成逻辑矛盾才允许返修。
- 修改影响先做确定的版本依赖传播，再由模型提出语义影响范围。没有覆盖证据，不以“未检索到”证明远处完全不受影响。
- 未修改的证据允许按条目复用，但必须记录复用范围、依赖未变和局限；不能只改报告顶部版本号。
- 单纯文字变化也产生新快照并使相关报告待核，但不自动要求重选题；人物关系、结局或主线等实质方向改变才触发对应范围重新确认。分类不确定时交代不确定性。
- 独立评审是职责与输入隔离要求，不默认多代理越多越好。可用独立上下文时使用；否则如实标自查／带历史复核。
- 制作未知、远端不可用、缺独立评审只限制相应声明和动作，不把所有工作统一阻断。
- 所有门槛只约束本工具及遵守协议的宿主；不能防止用户或外部模型直接编辑文件。接续时检测并处理，而非承诺无法绕过。

## Tests

### 1. 必须保持的不变量

- 原文件、用户现有改动、历史候选和历史决定不能被静默覆盖。
- 运行完成、格式通过、模型推荐、用户采用、制作放行、付费执行是独立事实。
- 当前版本不允许借用已失效报告作为完成证明。
- 候选状态不能更新远端正式事实；没有远端回执不能称已同步或采用。
- 只读动作不写项目状态；安装不启动创作、联网、上传或付费。
- 新流程启用与否不改变旧命令的默认统计语义。

### 2. 工程测试矩阵

测试覆盖：正常闭环；输入缺项；重复提交；相同键不同内容；中途终止；半成对象；清单损坏；两个本地写者；外部文件修改；路径越界；未知 schema；旧报告失效；范围越权；无来源审批；同名不同项目；远端超时后恢复；输入快照过期；无网络；新进程读取；升级后回退。

本地锁和原子性必须在宣称支持的平台实际测试；未测平台只报未验证。涉及 mali-story 状态的集成测试必须覆盖不同进程／不同连接，不只测试内存替身。DB 测试仅在明确安全测试库运行。

现有单元测试与分发校验仍运行。上轮的 50 项通过作为历史基线，不预先写成本次新功能验收结果。

### 3. 创作评估不是关键词测试

冻结旧版与新版方法，分别测试“能否发现问题”和“能否写出更合适的正文”。只测试评审不能证明写作改善。

首批评估规模建议：12 个原创或获许可场面，其中 6 个有已知缺陷、6 个是容易被误伤的有效写法；另加两个不同题材的三集连续样本检验跨集关系与因果。材料与判据在运行前冻结，开发题和保留题隔离。

缺陷覆盖：行为动机跳步、人物对白可互换、主题解释代替行动、反派无依据送分、关键知识缺口、跨集情绪归零。有效写法覆盖：静场、直接认错、合理成长、喜剧、克制人物和有意保留的矛盾关系。

在可固定的相同模型／宿主条件下，旧新方法各重复 3 次；模型身份或版本不可知则记录，不能作严格因果结论。中性编号、随机阅读顺序，保留全部答卷、失败和人工干预，不能只挑最好的一次。

报告按人物声音、心理过程、对抗、因果、情绪余波、有效细节损失逐项引用正文，允许平局或两者都不成立。不设“综合 85 分自动合格”；不给更长正文加分。作者和评审的熟悉度明确记录。

固定工程用例应全通过；已知严重缺陷仍漏检、有效静场被强制改写或出现新的人物同质化时，不宣称对应方法已验证。真人未判断时最多标模型对照结果，不声称用户偏好或稳定创作收益。所有模型运行均使用已授权环境，不自动增加付费调用。

记录每轮实际耗时、人工修订、模型调用与记录维护工作量作为基线；没有可比数据前不承诺提效比例。短样本通过不证明 60 集稳定性，后续只有在获准扩稿时才能补全跨批次及季末回收验证。

### 4. 实际项目试点

《镇渊君》仅使用已约定的 11–15、20–21 共七集，以及必要只读前后文。先登记现有样段及其状态验证流程；如需再次改稿，须处于有效的具体修订授权内，不能把本次架构方案当作扩稿许可。

不改 1–10，不扩写未授权集，不改第二季和已确认结局，不覆盖原飞书。用户确认语感之前不扩全稿。该案例进入私有验收，不进入技能分发。

## Human Acceptance Demo

工程演示可在 3–5 分钟内完成；七集阅读和导演试制另计，不承诺几分钟能判断剧本质量。

1. 打开一个无私人内容的测试项目，看到当前任务只允许改 11–15 集，并列出人物与情绪目标。
2. 登记候选 A 和绑定 A 的审查，看到事实检查、创作目标、采用、制作状态分列。
3. 在正文中手动改变一个影响后续的动作。再次检查，看到旧审查失效、受影响范围和需要重查的目标；正文没有被恢复旧版。
4. 中断会话，用新进程／新会话打开同目录，恢复同一候选、未决项和下一动作。
5. 登记修订 B 及复核，导出一页交付卡。卡片指向准确正文和版本，不把模型复核写成人工采用。
6. 模拟远端响应未知，观察系统显示待对账而不是自动重跑付费任务。

验收可见信号：版本变化能解释旧结论为何不再适用；未解决的人物目标保留下来；用户只需读正文和交付卡，不需手工维护状态账。

任一情况即拒收：旧审查继续给新版背书；后台偷偷改正文；把程序结果写成真人通过；缺信息时造 ID；为了过检把有效静场或合理成长机械改坏；要求用户填写大量表格才能改一场戏。

实施者提交前必须自行跑完演示、保存完整输出与差异、逐项核对 AC，列出所有不匹配。工程合并是否还需人工演示由实际证据决定；创作采用本身必须保留用户判断，导演制作决定不能由工程验收代理。

## Anti-Requirements

- 不做跨设备自动同步、多人同时写同一本地目录、全量知识图谱、语义依赖必然完整的承诺。
- 不默认增加代理数量、审查轮数、每批人工审批或付费模型调用。

### 3. 迁移和发布方案

1. 先记录当前源码、已安装包、配置和未提交改动。保留用户修改；不 reset、不覆盖、不自动提交。
2. 在独立测试项目运行新机制，默认不启用到已有作品。新目录可选；旧 CLI 不要求项目先迁移。
3. 对一个实际项目执行只读导入预览：列出原稿、候选、报告、可能审批证据和缺口。文件名 approved 不构成审批证明。
4. 确认目标后仅登记快照和来源；原正文、PROJECT 手写内容与远端状态不改。历史无证据项目记 unknown，不要求补造。
5. 第一次仅影子检查：新机制报告问题，但不自动批量改稿。比对误拦截和漏项，再启用本项目的动作检查。
6. 七集试点验证通过适用项后，形成候选版本和发行说明；发布、安装升级与项目采用分别记录。未验证联网功能保持关闭。
7. 回退时停用新工作流入口，保留全部新候选、回执和历史记录，继续使用旧工具。技能回退遵守现有 installer 所有权／修改检测；不通过回滚安装把用户新稿删掉。

### 4. 风险与停止条件

| 风险 | 发现信号 | 处置 |
| --- | --- | --- |
| 文书负担超过收益 | 一场修订要重复维护同一事实多次，正文时间被记录吞掉 | 单一来源生成摘要；删去无消费方字段；保留版本、目标和引用 |
| 新规范把戏磨平 | 对照稿更工整但人物更同质、有效静场被改坏 | 不推广该方法改动，回到场面方案比较；保留技术底座成果 |
| 依赖分析误称精确 | 漏掉真实后果，或大量全季失效无法说明原因 | 扩大审查、标 unknown；先保证诚实，不做全量图谱工程 |
| 宿主或接口不兼容 | 无独立上下文、schema 不适配、缺权限或分页未读完 | 降级为本地／自查／覆盖不足，不伪造功能 |
| 远端未知导致重复成本 | 请求后无回执、费用状态不明 | 保存请求标识并对账，不自动再执行 |
| 多仓库状态分裂 | 本地称已采用，远端无对应回执 | 本地撤销错误投影并保留记录，重新读正式状态 |
| 范围失控 | 为修一项引入新 UI、数据库、模型代理系统 | 停止该扩展，单列必要性与用户决定，不借重构顺手实施 |
| 制作证据继续缺失 | 无法说明真实片长、资产、成本 | 维持未放行；不阻断无依赖的本地验证 |

R2 后若可靠的登记／失效／恢复链路仍无法在约定单机范围成立，先修这一链路，不扩展功能。R4 若创作对照没有收益，技术底座可以保留，但不得把方法版本标为“质量提升已验证”。

### 5. 完成定义与责任

- 工程完成：适用 AC 的可重复证据、旧命令兼容、安装与回退演示、能力清单齐备，由工程负责人和未参与该部分实现的复核者验收。无法独立复核则记录未完成，不冒充独立通过。
- 创作方法验证：提供旧新完整样段、具体收益与损失、重复与保留题结果；模型和真人判断分别记。不是程序测试的附属项。
- 本剧扩稿：只由用户对七集语感及相应范围的明确决定触发。
- 制作复工：由导演／制片根据具体版本和真实条件决定；付费执行需另有权限。
- 用户不承担技术状态维护；AI／工具负责记录，用户只做必要的创作与制作决定。

### 6. RD Loop Handoff

- Intake source：用户在架构诊断后明确要求完整重构方案与计划。
- Priority signal：已有停产和多轮修订未满足人物／情绪目标的反馈；不能再以规范数量或格式检查代替结果。
- Workflow recommendation：分阶段 refactor + 边界明确的 feature；保持现有产品入口和授权模型。
- Automation mode：建议后续本地实施；本轮仅方案，不启动任何自动开发或外部任务。
- Implementation Contract required：yes；R1 固定契约后，各单元沿同一版本实施。
- Visual contract required：no；无页面变化。
- Independent verification required：yes；以故障恢复、版本失效、迁移回退、实际样段和能力回执为依据，不只看测试数量。
- Known blockers：整体实施尚未授权；联网部署与权限未在本轮验证；用户语感确认及导演制作证据未取得。前两项分别限制实施／联网集成，后两项只限制对应采用和制作结论。
- Scope boundary：主要修改 drama-studio 自包含分发、测试、评估和文档；mali-story 先复用，只有已证实的接口缺口才单列变更；不动私有正文、飞书、付费任务和正式采用状态。
- Feedback tags：workflow-not-enforced、stale-review、character-voice、emotional-continuity、context-selection、candidate-vs-adopted、production-unknown。
- Next action after approval：从 R0/T01 启动；首个工程里程碑是 R2 的纵向链路，不是再写六份泛化原则，也不是直接扩写整季。

本方案按 drama-studio 的创作边界和 Spec 的需求／验收结构编制。为响应本次技术重构请求，补充了架构、数据与接口决策；没有进入 GitHub、项目配置初始化或开发调度流程。
