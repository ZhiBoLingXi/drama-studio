# R2：本地版本、失效与恢复的纵向链路

设计状态：已拆分待审；实现状态：planned。预计 4–6 个工程工作日。对应 T03、T04。

## 1. 目标与入口

入口为 R1 冻结契约及 R0 基线。交付一个不需要模型或网络也能演示的完整链路：登记输入与候选 → 绑定审查 → 外部修改 → 旧证据失效 → 新进程恢复 → 导出精确版本。

本阶段验证执行可靠性，不生产真实审稿结论。演示里的预制报告必须标 fixture，不冒充模型阅读。

## 2. 存储与提交设计

### 2.1 存储形态

在显式启用项目的 `.drama/workflow/` 中存不可变内容对象、元数据对象和单一 manifest。manifest 持有修订索引、edition／run 引用、operation 索引和清单修订号。大量正文不重复嵌入清单。

原工作文件、`.drama/project.json` 和用户写的 PROJECT.md 不变为数据库。新机制未初始化时 inspect 只报告缺失，不能顺手创建目录。首次明确 register 可在版本预期为初始值时创建新工作流。

### 2.2 一次提交的顺序

1. 校验项目路径、契约、输入引用和授权适用范围；将工作文件读为确定快照，发现读取期间变化则失败。
2. 构造稳定 operationId 对应的请求指纹及候选内容对象。
3. 取得已支持本地文件系统上的排他写锁，重读 manifest。
4. 先核对 operation 索引：完全相同的既有操作直接返回原结果；不同内容复用同键返回冲突。未命中再核对 expectedRevision。
5. 写新的不可变对象并完成所需落盘；已有同名内容地址对象须验证一致，不覆写损坏对象。
6. 写临时新 manifest，验证引用齐全后原子替换旧 manifest，再按支持平台要求同步目录。
7. 返回包含提交修订和操作结果的回执。提交已完成但响应丢失时，同请求重试能找回既有结果。

同一 manifest 的替换是本地提交点；不维护另一份必须同步写入才能恢复的“权威日志”。历史事件作为不可变对象被清单引用。提交前遗留的无引用对象不算成功，不自动删除。

锁仅在提交期间持有，不跨模型生成或用户阅读。跨主机并发和网络盘不支持；无法满足锁／原子替换前提就拒绝登记，仍允许明确的只读检查。损坏清单不能根据文件时间戳自动拼出“最新正确状态”。

### 2.3 检查与执行竞态

先前 check 结果只是观察。提交、输入冻结和导出实际执行前必须重新核对源摘要及清单版本。已经保存的不可变候选可以如实返回；不能因为它来自旧前文就假称其来源仍新鲜。

## 3. 失效和恢复设计

登记 dependencies 是明确的“谁使用了哪个版本及范围”。输入修订变化后传播 stale；依赖覆盖不完整时输出 unknown 和待查范围，不能以没有边证明没有剧情关联。

报告是历史事实，失效是针对新目标计算的适用性，不改写旧报告内容。允许按证据条目复用，但必须核对条目所依赖原文；不能把报告整体换个目标 ID。

resume 只给出已保存步骤、未决项、外部修改、未知调用和下一动作。进程在生成中消失且无结果文件时，不称已经写完；是否重新调用模型由宿主依授权决定。远端费用未知交给 R5 对账。

## 5. 接口与修改边界

新增代码归自包含技能内 `scripts/workflow/`，命令路由只在 `drama_tools.py` 薄接入；测试归 tests。统一契约由 R1 消费，不复制第二套 schema。

export 从固定 edition 读不可变正文，生成纯正文和状态卡两个分离入口。目标目录必须明确且未被不同内容占用；重试核对既有导出内容，不用强制覆盖。若导出文件已生成而回执未提交，恢复时只在来源与文件均一致时补登记，否则保留为未确认产物。

不新增模型、后台调度、网络客户端、云数据库或静默项目迁移。

## 6. 验收、回退与交接

重点负例：并发都以 revision 3 提交；同操作重试时 manifest 已推进；清单替换后进程退出；文件内容相同但项目不同；报告全文范围只有三集却目标为五集；外部新增正文不能被自动纳入 edition。

阶段出口必须同时给出测试、演示和限制。数据覆盖、重复业务操作或旧报告背书任一问题未解决，不扩展默认启用范围。

回退停用新入口，保留对象与原稿；不要删除 `.drama` 或自动回退用户工作文件。交给 R3 的是可写可读的契约实现，交给 R4 的是版本绑定而非“已独立审查”。
