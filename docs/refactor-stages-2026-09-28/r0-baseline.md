# R0：冻结基线、能力与保护范围

设计状态：已拆分待审；实现状态：planned。预计 1–2 个工程工作日。对应 T01。

## 1. 问题与目标

必须先回答：真正要补什么、已有能力在哪、哪些文件已有用户修改、测试目前证明什么。当前工作区不是干净基线，不能只记录 Git HEAD 后把未提交改动丢掉。

出口是可追溯的改造起点，不是重新审完整剧或重新研究产品定位。

## 2. 输入与输出

输入：总方案、两个仓库当前工作区、已安装技能回执、既有测试与创作评估、用户已表达的质量问题和样段范围。只读取任务相关材料，不扫描无关私人目录。

输出：baseline-index、capability-matrix、protected-scope、evaluation-charter 和 baseline-receipt 五项逻辑产物，可合并为一份小型基线包。源文件不复制进发行包；需要冻结的私有材料留在私有项目。

## 3. 设计决定

### 3.1 基线必须能区分四种状态

源码及未提交修改、安装版及其修改、已部署工具能力、实际项目运行证据分别记录。每项含读取时间、范围、指纹或回执、能证明和不能证明的事项；不能写一个“当前版本”掩盖差异。

### 3.2 能力盘点按消费路径组织

每项远端能力记录输入形态、源码位置、宿主发现情况、认证／业务读情况和预期消费任务。源码存在但没有消费方，记为“待衔接”；接口存在但输入不兼容，不能记为可复用完成。

本阶段可做只读能力发现；不通过创建项目、任务、候选或计费调用来证明可用。

### 3.3 测试材料先定义权利和盲测边界

工程 fixtures 与创作题分开。创作材料区分开发集、保留集、私有实剧；先写每题要观察的失效机制、允许成立的替代写法和判定局限。没有题目许可不进入分发；已被开发者看过的答案不能宣称对开发者盲测。

当前七集仅为私有试点，不扩大授权，不因接入流程改动正文。长期评估包括不同题材，不让《镇渊君》的特定人设变成通用规定。

## 5. 验收、演示与反例

演示：同一处代码已有未提交修改，但安装版仍是旧文件；基线同时显示两者，不自动安装。测试失败时报告失败及影响，不先修代码后谎称原基线通过。

反例：测试脚本存在不代表测试已跑；候选在飞书存在不代表用户采用；本机模型历史包含旧反馈不代表冷读。

本阶段为 AC-01、AC-17、AC-18 提供前置，不单独宣布它们最终通过。

基线候选命令为仓库已有的 `python3.11 -B -m unittest discover -s tests -v`、`python3.11 -B scripts/validate.py`，以及目标确为 Codex 安装时的 `python3.11 -B scripts/install.py verify --host codex`。执行前核对实际解释器和宿主；不存在对应安装则记未配置，不创建安装来使检查变绿。

## 6. 修改边界、回退与交接

实施时允许写新增基线记录和原创测试材料；既有应用、技能、安装目录和私人正文只读。若测试需要有副作用环境，先隔离到明确测试目录／安全库；不能影响共享数据库。

输出不合格只修正记录并保留历史，不 reset 工作区。交给 R1 的是明确版本的基线包；后续发现状态漂移追加新观察，不能悄悄改最初证据。
